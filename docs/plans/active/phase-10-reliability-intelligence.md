## Decisions needed from the user (each with a recommended default)

1. **Where detectors run.** Recommended: a separate `detect_findings` outbox job enqueued by the summarizer (D1), not inside `summarize_run`. It costs one more read of the run's events per debounce window, in exchange for summary freshness and `summary_state` being untouched by detector cost or bugs, and for re-running detectors without re-summarizing.
2. **Thresholds.** Recommended: deployment-wide settings (`ABB_FINDINGS_*`, defaults in code, every threshold used is recorded in the finding's evidence). Per-project thresholds are deferred to Phase 14 (policy configuration), not built now (D6).
3. **False positives.** Recommended: no dismiss/acknowledge workflow this phase. Findings are labelled `probable` or `deterministic`, carry a stable `fingerprint` so a later dismissal table can key on it, and a successful run's loop finding is `info`, not `warning` (D7).
4. **Cost spike baseline.** Recommended: the same project and agent, the newest 200 finished runs of the previous 30 days, at least 20 of them, nearest-rank p95 (D5). Alternative: skip the cost-spike detector until analytics keep cost percentiles (it is the only detector that depends on data outside the run).
5. **Health.** Recommended: per-run dimensions (`reliability`, `tool_reliability`, `cost_efficiency`, `loops`, `context`) each `ok | warn | bad | no_data` with the inputs and the rule that produced it, and no numeric score; the spec's `85/100` example is set aside (ADR-081). Agent-level health across runs is a follow-up on the analytics rollups.
6. **UI placement.** Recommended: a "Findings" panel on the run page (health dimensions, findings with "Show evidence" jumps into the timeline) and a findings column on the runs list; no new navigation entry or page (keeps `AppShell` untouched).

## Outcome

A developer opening a run that looped, retried itself into the ground, grew its context without bound, cost far more than its siblings, failed tool after tool, or simply failed, sees *why* in words, with every claim linked to the events that prove it: "The agent repeated `search -> read -> reason` 11 times in 37 s (events 120-186)", "`db.query` failed 4 times in 9 calls, with 3 retries between", "Failed with exit code 2 from `shell` after the test suite failed; the files changed before it were ...". Deterministic conclusions are stated as facts; heuristics are labelled "probable". Findings are derived records: a job rebuilds them from the run's events (INV-2), each records the detector version that produced it (§81.2), and an operator can re-run every detector after a rule change. Nothing in a finding reveals captured content, so a VIEWER sees exactly what an OWNER sees. The product acceptance in the roadmap holds: seeded pathological runs are detected with links to evidence, detector fixtures are committed, and probable conclusions are labelled.

## Non-goals

SDK-side loop detection (the SDK keeps emitting `loop.detected` when an integration reports one; the server records it as a finding), alerts and notifications (Phase 17), findings in analytics rollups and agent-level health across runs (follow-up KI; ADR-043's tables are untouched), a dismiss/acknowledge workflow, per-project or per-agent thresholds (Phase 14), model-judged or ML root causes (§85.4), incremental summarization (KI-016 proper), time spent retrying (ADR-042), multi-agent failure chains across child runs (Phase 9 owns child-run semantics), security findings and server-side secret detection (Phase 13), evaluations (Phase 11), full-text search over findings (Phase 16), a `findings_updated` SSE frame (the run page polls the findings route while the run is active), a project-wide findings list route (the runs list carries a per-run badge). Nothing here needs Kafka, ClickHouse, Redis or Kubernetes.

## Decisions (D1..D10; ADR drafts in the appendix)

- **D1 (ADR-080) Detectors run in their own outbox job, `detect_findings`, enqueued by the summarizer.** `summarize_run` enqueues `detect_findings` with dedupe key `f"{workspace_id}:{run_id}"` (same format as `summarize_key`; job types differ so keys never collide) in the transaction that writes the summary, delayed by D3. The handler takes `pg_advisory_xact_lock(hashtextextended('findings:' || workspace_id || ':' || run_id, 0))` (one writer per run for findings; no contact with the run row lock, so neither summarization nor ingestion waits on it), reads the run row (status, typed figures, project, agent, `ordering_mode`), loads the events capped (D3), derives spans, runs every detector (pure functions), queries the cost baseline (D5), and rewrites `findings` and `run_findings` for the run (delete + insert, idempotent, INV-2). Rationale over "inside the summarizer" (ADR-040's choice for cost): the summary is what every list and stream shows and must stay fast and never `failed` because a heuristic threw; §72.2 names the anomaly detector a processor of its own; the roadmap says "detectors as processors over the outbox"; re-running detectors after a rule change should not re-derive spans and cost; a detector dead-letters its own job. Cost: one more event read per run per debounce window, bounded by D3 and measured by AC-11. Rejected: computing findings at read time (O(events) per page view; not versioned); a separate worker process (same image, same queue; nothing to gain yet).
- **D2 (ADR-080) Storage: `findings` (one row per finding) and `run_findings` (one row per run), both derived.** `findings (workspace_id, id, run_id, project_id, agent_slug, run_started_at, detector, detector_version, finding_type, kind, severity, confidence, start_event_id, end_event_id, fingerprint, evidence, created_at)`; `run_findings (workspace_id, run_id, project_id, detectors_version, summary_version_seen, computed_at, event_count_seen, truncated, finding_count, max_severity)`. The run owns its findings (composite FK to `runs`, `ON DELETE CASCADE` like `spans`); `project_id` and `run_started_at` are copied so a later project-level listing or rollup needs no join (ADR-043's pattern). `id` is a fresh `fnd_` ULID per write (new `IdKind.FINDING`); identity across rebuilds is `fingerprint = sha256(detector | finding_type | start_event_id | key)` where `key` is the detector's stable identity (the pattern tokens, the argument hash, the retry scope span, the failure category), unique per run. `evidence` is a JSON object (CHECK `jsonb_typeof = 'object'`, `pg_column_size < 16384`). The runtime role keeps full DML (derived tables are rewritten; `test_runtime_role.py` covers this automatically because the tables are not in `APPEND_ONLY_TABLES`). Rejected: findings inside `runs.summary` JSONB (no per-finding ids, no evidence bound, every list pays for it); appending versions instead of rewriting (unbounded growth per run; the version is on the row and the rebuild is the history).
- **D3 (ADR-080) Bounded and adaptive.** `PgEventStore.load_run(run_id, limit=None)` gains an optional cap applied in the run's stored `ordering_mode` (`ORDER BY sequence, event_id` or `ORDER BY occurred_at, event_id`; the result is then `sort_events`-ed as today). The handler passes `settings.findings_max_events` (default 50,000) and records `event_count_seen` and `truncated` on `run_findings`; the API and UI say "analysed the first 50,000 of N events". The summarizer's enqueue delay is `clamp(findings_delay_seconds * max(1, event_count / 10_000), findings_delay_seconds, 60)` with `findings_delay_seconds` default 5 s, so a 30,000-event run is re-analysed at most every 15 s while it grows and once more after it ends (the summarizer always enqueues, and coalescing folds the rest). Detectors are O(n) in events (sequence detection is bounded by pattern length <= 8 and a single pass per length) and never copy payloads: a payload is hashed once and dropped.
- **D4 (ADR-080) Detector versioning and re-run.** Every detector is a class with `name`, `version` (semver string, `detector_version = f"{name}@{version}"` as in §81.2) and `detect(ctx) -> list[Finding]`. `DETECTORS_VERSION` (an integer, like `SUMMARY_VERSION`) is bumped whenever any detector's rules or the evidence contract change and is stored on `run_findings.detectors_version`; the findings route reports `state: outdated` when the stored version is older. Re-run: `python -m abb_api.cli rebuild-findings --workspace W [--project P] [--since T] [--limit N<=10000]` enqueues `detect_findings` for the newest runs (the `rebuild-costs` pattern, audited as `findings.rebuild` with actor `cli`). No HTTP rebuild route this phase (the one for cost exists because BILLING people change prices from the UI; a detector version only changes with a deployment).
- **D5 (ADR-080) Cost spike is the one baseline detector.** For a terminal run only: baseline = finished runs (`SUCCESS, FAILED, TIMED_OUT, BLOCKED`) of the same workspace, project and `agent_slug`, started before this run and within `findings_cost_spike_window_days` (30), newest 200 by `started_at` (`ix_runs_project_started`, filtered on `agent_slug`; bounded by the window), requiring at least `findings_cost_spike_min_baseline` (20). A finding is raised when `cost_usd > p95` (nearest rank) **and** `cost_usd > 2 x median` **and** `cost_usd >= 0.01`. The evidence stores the baseline (`n`, `median_usd`, `p95_usd`, `window_days`, `newest_started_at`) so the finding is explainable and the row is self-contained; a later rebuild may legitimately differ because the baseline moved, which the ADR states. It is `probable` with confidence 0.6 (0.8 above 5 x p95).
- **D6 (ADR-081) Thresholds are deployment settings, recorded in evidence.** `Settings` gains `findings_delay_seconds` (5), `findings_max_events` (50,000), `findings_loop_min_repetitions` (3), `findings_identical_min_count` (3), `findings_retry_storm_min` (5), `findings_retry_burst_window_seconds` (60), `findings_context_growth_min_tokens` (20,000), `findings_context_growth_factor` (2.0), `findings_cascade_min_failures` (3), `findings_cascade_window_calls` (10), `findings_cost_spike_min_baseline` (20), `findings_cost_spike_window_days` (30), all `ABB_FINDINGS_*`, validated (`ge`). Each finding's `evidence.thresholds` lists the values it used. Per-project thresholds would need a table, a write route, an action, UI and audit: Phase 14 (policy configuration) owns that; the detector context already takes a `DetectorConfig` so only the source of the config changes then.
- **D7 (ADR-081) Probable versus deterministic, severity, and no dismissals.** `kind = deterministic` when the finding restates typed events (N retries happened; N identical calls were made; the run failed with exit code 2) with `confidence = 1.0`; `kind = probable` for interpretations (a loop, context growth, a cost spike, a heuristic cause) with `confidence` in `[0.5, 0.95]` from the rule's own evidence (for example repetitions). Severity: `info | warning | critical` per detector (table below); a `probable` loop on a run that succeeded is `info`. The UI labels probable findings "Probable" in text, never only by colour. No dismiss or acknowledge in this phase: findings are rewritten wholesale, so a dismissal needs its own table keyed on `fingerprint`, a write action and audit; the `fingerprint` exists now so that table can be added without a rebuild.
- **D8 (ADR-080) Evidence is metadata only, by construction.** Evidence values may be: event ids, span ids, event types, counts, durations, token counts, costs, hash prefixes (12 hex chars of a SHA-256), `tool.name`, `llm.model`, `llm.provider`, `llm.error_type`, `tool.error_type`, `shell.exit_code`, `shell.risk_class`, `shell.category`, `http.status_code`, `db.operation`, `file.operation`, `test.failed`/`test.total`, `retry.attempt`, `loop.pattern` tokens (built from event types and tool names), `policy.id`, `policy.capability`, status names and the thresholds. Never: anything in `CONTENT_ATTRIBUTES`, a span name, a payload, a payload excerpt, `run.name`, tags, run `metadata`, `retry.reason`, `policy.reason`, free-text error messages. Enforced three ways: the `Finding` model validates evidence against an explicit key allowlist per detector; a unit test runs every detector over events built from the canary world's content values and asserts none appears in any evidence or message; the route is in the registry so `test_content_withheld.py` and `test_cross_workspace.py` cover it for every actor. Consequence: no per-actor projection is needed; a VIEWER and an OWNER get identical findings bodies (AC-7). Messages (`title`, `message`) are generated at read time from the typed evidence by one `describe(finding)` in Python, so the wording lives in one place and is never stored.
- **D9 (ADR-081) Health is a set of explained dimensions, not a score.** Computed at read time from the run row and its findings by a pure `health(run_facts, findings) -> list[Dimension]`: `reliability` (status, `error_count`, `retry_count`), `tool_reliability` (`tool_spans_ok / tool_spans_finished`: ok >= 0.95, warn >= 0.8, bad below; `no_data` without finished tool spans), `cost_efficiency` (`retry_cost_usd / cost_usd`: ok < 0.1, warn < 0.5 or a cost-spike finding, bad >= 0.5; `no_data` when cost is 0), `loops` (none: ok; a probable loop or identical-request finding: warn; critical: bad), `context` (by the context-growth finding's severity). Each dimension returns `status`, `inputs` (the figures), `rule` (one sentence) and `finding_ids`. `overall` is the worst status, as a word. No `0-100`; nothing is weighted. Rationale: the roadmap forbids an unexplained score and the spec's example weights are arbitrary; a dimension with its inputs is what a developer can act on. Rejected: storing health on `run_findings` (it is a function of two derived tables; recomputing per read is microseconds).
- **D10 Failure chain is a finding, not a separate resource.** `failure_chain` (detector `failure-chain`) is produced for runs whose status is `FAILED | TIMED_OUT | BLOCKED` or that contain `run.failed`: the terminal event, the root error event, the span lineage, preceding errors on that lineage (<= 20), retries scoped to it, and mutations (`file.*`, `git.commit`) between the last known-good action (the last successful `tool.call | shell.command | db.query` closer before the first error of the chain) and the terminal event (<= 50). It carries the deterministic category of §80.2 (`command_failure | external_service_failure | provider_failure | policy_termination | timeout | tool_failure | unknown`) as `kind = deterministic`; the heuristic causes of §80.3 are separate `probable_cause` findings (D7) so each carries its own confidence. The UI renders the chain as an ordered list of linked events. Rejected: a `/failure-graph` route and a graph model (nothing consumes a graph yet; the chain is the §80.1 list, which the finding contract already expresses).

| `context-growth@1.0.0`, type `context_growth` | `llm.input_tokens` of `llm.request.completed` in canonical order: a non-decreasing stretch of >= 5 calls whose last value >= 2.0 x its first and >= 20,000 tokens. | probable, `warning` / `critical` at >= 150,000 tokens, confidence 0.7 (0.85 at >= 10 calls) | `calls`, `first_tokens`, `last_tokens`, `growth_factor`, `series` ([{`event_id`, `input_tokens`}] <= 50, sampled evenly), `start_event_id`, `end_event_id`, `thresholds` |
| `cost-spike@1.0.0`, type `cost_spike` | D5. Terminal runs only. | probable, `warning` / `critical` above 5 x p95, 0.6 / 0.8 | `cost_usd`, `baseline` {`n`, `median_usd`, `p95_usd`, `window_days`, `newest_started_at`, `agent_slug`}, `thresholds` |
| `tool-failure-cascade@1.0.0`, type `tool_failure_cascade` | Over closers of `tool.call | shell.command | db.query` and `http.response` with status >= 500: a sliding window of 10 such calls containing >= 3 failures (`.failed`, or status `error|timeout`); merged into one stretch per overlap; <= 50 per run. | deterministic, `warning`, `critical` if the run failed, 1.0 | `failures` ([{`event_id`, `event_type`, `tool_name`, `error_type`, `exit_code`, `status_code`}] <= 20), `calls_in_window`, `retries_between`, `alternates` (tool names used after a failure, <= 10), `start_event_id`, `end_event_id`, `thresholds` |
| `failure-chain@1.0.0`, type `failure_chain` | D10. | deterministic, `critical` if the run failed else `warning`, 1.0 | `category`, `terminal_event_id`, `root_event_id`, `chain` ([{`event_id`, `event_type`, `role`: `terminal|root|error|retry|mutation`, `span_id`}] <= 50), `span_lineage` (<= 20), `retries_caused`, `retries_unattributed`, `mutations` (count) |
| `failure-chain@1.0.0`, type `probable_cause` | §80.3: `code_change_before_test_failure` (a `file.modified|created` precedes a `shell.command.*` with `test.failed > 0` inside the chain), `repeated_tool_timeout` (>= 2 `timeout` statuses or `timeout.occurred` on one `tool.name`), `context_overflow` (`llm.request.failed` with `llm.error_type` matching `context|token|length`), `invalid_tool_arguments` (`tool.error_type` matching `argument|validation|schema|param`). | probable, `warning`, 0.5-0.7 | `cause`, `event_ids` (<= 20), `tool_name` / `model` where relevant |
| `reported-loop@1.0.0`, type `reported_loop` | Each `loop.detected` event (an integration said so). | deterministic, `warning`, 1.0 | `pattern` (`loop.pattern`), `repetitions`, `event_id` |

Every detector is order-independent (it sorts nothing itself; the context is canonically ordered once) and tolerant of hostile attributes (a missing or wrongly typed value is skipped, never raised on). A detector *bug* (an exception) is not swallowed: the job fails and retries like any handler and dead-letters after five attempts, which the route reports as `state: failed`; a bug must surface, and the summary is unaffected (D1).

## Proposed design

### API (`apps/api/src/abb_api/findings/`)

- `model.py`: `Finding` (frozen dataclass: `detector`, `detector_version`, `finding_type`, `kind`, `severity`, `confidence`, `start_event_id`, `end_event_id`, `fingerprint`, `evidence`), `Severity`, `Kind`, `DetectorContext`, `RunFacts` (status, counters, cost, agent, project, started_at), `CostBaseline`, `DetectorConfig` (from `Settings`), `EVIDENCE_KEYS: dict[finding_type, frozenset[str]]`, `validate_evidence()`, `fingerprint()`, bounds (`MAX_PER_DETECTOR = 50`, `MAX_PER_RUN = 200`, `MAX_IDS = 50`).
- `detectors/`: one module per detector (`sequence.py`, `identical.py`, `retries.py`, `context.py`, `cost_spike.py`, `cascade.py`, `chain.py`, `reported.py`), `DETECTORS: tuple[Detector, ...]`, `DETECTORS_VERSION = 1`, `run_all(ctx) -> list[Finding]` (applies the per-detector and per-run caps, sorted by `(severity desc, start position, detector)`).
- `tokens.py`: the normalisation of events to tokens shared by the sequence and cascade detectors.
- `describe.py`: `describe(finding) -> (title, message)`; wording for every `finding_type`; "Probable:" prefix for `kind = probable`.
- `health.py`: `health(facts, findings) -> HealthOut` (D9).
- `repository.py`: `FindingsRepository(conn, tenant)`: `replace_run(run_id, project_id, agent_slug, run_started_at, findings, state)`, `for_run(run_id) -> (RunFindingsState | None, list[FindingRecord])`, `badges(run_ids) -> dict[run_id, Badge]` (count, max severity, detectors_version), `cost_baseline(project_id, agent_slug, before, *, window_days, limit) -> list[Decimal]`.
- `service.py`: `FindingsService.get(principal, run_id)`: `RunService.visible_run` (404 rules unchanged), repository, outbox-derived job state (`RunQueries.summary_states` generalised to take the job type; `detect_findings` -> `processing | failed`), version comparison -> `outdated`, `none` when no row yet, else `current`; attaches `truncated`.
- `router.py`: `GET /v1/runs/{run_id}/findings` (`require(actions.RUN_READ)`, `_ERRORS` like `runs/router.py`), response `RunFindingsOut { run_id, state: { status: none|processing|current|outdated|failed, detectors_version: int|null, computed_at, event_count_seen, truncated }, health: HealthOut, items: list[FindingOut] }`; `FindingOut { id, run_id, detector, detector_version, finding_type, kind, severity, confidence, title, message, start_event_id, end_event_id, fingerprint, evidence, created_at }`. Included from `main.py` after `runs_router`.

## Security review note (mandatory adversarial pass)

Scenarios the reviewer must attempt (expected result in parentheses):

1. Content through evidence: ingest a run whose `shell.command`, `shell.cwd`, `file.path`, `git.repo`, `http.url`, `test.failing`, `span.name`, `run.name`, tags, run `metadata`, `retry.reason`, `policy.reason` and payloads contain canaries; read findings as every actor (no canary anywhere, including `title`/`message`, for OWNER too); a `custom.*` event with a `thing.command` attribute (never copied: evidence keys are an allowlist, not a denylist).
2. Hash oracle: identical-request evidence exposes only 12 hex characters of a SHA-256 of the canonical payload (no way back to the payload; a reviewer confirms the full digest is not stored anywhere).
3. Tenant isolation: findings for a foreign or random run id (404, identical body); the cost baseline for an agent slug that exists in both tenants (counts only the caller's workspace; test with the canary tenant's 777.777 runs); `rebuild-findings --workspace` for a workspace the CLI user names (CLI is trusted; the audit row names the workspace).
4. Authorization: BILLING (403 `PERMISSION_DENIED`), a key without `runs:read` (403 `INSUFFICIENT_SCOPE` with `required_scope: runs:read`), HEAD/OPTIONS, a removed member mid-poll (401/404 as for runs), a project-bound key for a run of another project (404).
5. Resource exhaustion: a run engineered to produce thousands of candidate findings (50 per detector, 200 per run, evidence under 16 KiB, ids lists of 50); a 60,000-event run (cap, truncation flag); 1,000 events in one second for one run (coalescing: one job per delay window; the adaptive delay grows); a run whose events have 8 KiB attributes each (hashed, never copied); a `loop.pattern` list of 10,000 entries (evidence stores at most 20 tokens, each truncated to 64 characters); a `tool.name` of 10,000 characters (truncated to 128 in evidence, like rollup names).
6. Job isolation: a detector that raises (its job dead-letters after 5 attempts; `summary_state` stays `current`; the findings route says `failed`); a job for a deleted or unknown run (no-op); a job that outlives its lease (heartbeat; the advisory lock prevents double writes).
7. Logs: no evidence, payload, attribute value or message in any log line (structured logs carry `run_id`, `detector`, counts and `duration_ms` only); the log-hygiene pattern of `test_ingestion_api.py` extended to the job.
8. Determinism: two rebuilds of the same run give the same fingerprints; a changed `DETECTORS_VERSION` without a rebuild shows `outdated`, never stale findings presented as current.
9. UI: evidence strings render as text (no HTML); the "Show evidence" jump for an event id that is not in the loaded events (filtered or not yet paged) fails soft (no crash, a notice); a finding with 50 chain entries does not blow the layout on mobile.
10. Bounds on inputs to the detectors: NaN/inf/negative token counts, `shell.exit_code` as a string, `occurred_at` ties, cyclic `parent_span_id` (the chain's lineage walk is cycle-safe like `retry_call_ids`), events of two agents in one run.

## Risks

1. **False positives on legitimately repetitive agents** (a loop over 20 files looks like `read -> edit -> test` x 20). Mitigation: `probable` with "Probable:" in the title, `info` on successful runs, repetitions and duration in the evidence, thresholds configurable per deployment; the identical-request detector (payload hashes) is the deterministic companion that distinguishes a true loop. Dismissals are a named follow-up keyed on `fingerprint`.
2. **Worker cost on huge runs** (a second full event read per run; KI-016 tail). Mitigation: the cap, the adaptive delay, the `make bench` gate (AC-11) with a stated budget and a tuning loop; the summarizer path is unchanged.
3. **Content leakage through evidence or messages.** Mitigation: allowlisted evidence keys per finding type, canary tests over every actor, no per-actor projection to get wrong, review scenario 1.
4. **Merge conflicts with Phases 9, 11 and 16.** Mitigation: the "Merge notes" below; no change to the matrix, actions, `AppShell`, `quality.sh` or `runs/summary.py`; generated artifacts regenerated in the last commit of the step that changes them; the CSS block is appended.
5. **Tautological fixtures** (expected findings written from the detector's output). Mitigation: `*.expected.json` is hand-written from the scenario description before the detector runs, reviewed in the PR, and the mutation checks (a threshold change must break a fixture).
6. **Cost-spike noise** (small baselines, cheap runs). Mitigation: D5's three conditions and the minimum baseline; the evidence shows the baseline so a reader can judge; the detector can be switched off by `ABB_FINDINGS_COST_SPIKE_MIN_BASELINE` above any plausible count (documented).
7. **Schema drift between the finding model and the UI.** Mitigation: `FindingOut.evidence` is typed per `finding_type` in OpenAPI (a discriminated union would be ideal; a documented `dict` with per-type keys in `api-v1.md` is the minimum), the web types regenerated, the fixtures reuse the Python-generated expected JSON where possible.
8. **Flaky E2E timing** (findings arrive after a job delay). Mitigation: the script sets both delays to 0 and polls `state.status` with a bound, as `analytics-e2e.sh` does for rollups.

## Appendix: ADR drafts (written at step 7 as `docs/decisions/ADR-080-*.md` and `ADR-081-*.md`; the files are authoritative)

### ADR-080: Findings are derived, versioned, metadata-only records produced by a bounded detector processor over the outbox

**Context.** Spec §81 asks for deterministic detectors over windows of events with a versioned finding contract (§81.2: type, severity, confidence, start/end event ids, evidence, detector version) and §80 for an evidence-based failure analysis; §72.2 lists the anomaly detector as a processor; INV-2 requires derived state to be rebuildable; ADR-061 withholds captured content from actors without `payload.read`; KI-016/022 make any new per-run pass over events a cost to bound.

**Decision.** (1) A `detect_findings` outbox job, enqueued by `summarize_run` in its transaction (dedupe per run, delay growing with the run's event count, capped at 60 s), reads the run row and at most `ABB_FINDINGS_MAX_EVENTS` events in the run's canonical order, derives spans, runs every detector as a pure function and rewrites `findings` and `run_findings` for the run under a per-run advisory lock (one writer, no contact with the summarizer's row lock). The summarizer, `summary_state` and the stream are untouched; a detector failure dead-letters its own job. (2) Findings are rows keyed by the run (composite tenant key, cascade), with `detector_version` (`name@semver`), `kind` (`deterministic | probable`), `severity`, `confidence`, start/end event ids, a stable `fingerprint` and a bounded JSON `evidence`; `run_findings` records `detectors_version`, `event_count_seen` and `truncated`. A bump of `DETECTORS_VERSION` marks stored findings `outdated`; `rebuild-findings` re-derives (bounded, audited). (3) Evidence is metadata by construction: an allowlist of keys per finding type (ids, types, counts, hashes, tool and model names, exit and status codes, thresholds); never a content attribute, span name, payload, run name, tag, metadata or free-text reason. Titles and messages are generated at read time from the typed evidence. Consequently the route needs no per-actor projection and a VIEWER sees what an OWNER sees. (4) The cost-spike detector is the one that reads beyond the run (a bounded baseline of the same agent's recent finished runs); its evidence stores the baseline, and a rebuild may differ when the baseline has moved. (5) Bounds: 50 findings per detector, 200 per run, 50 ids per list, evidence under 16 KiB, names truncated to 128 characters.

**Alternatives.** Detectors inside `summarize_run` (one snapshot, no second read; rejected because summary freshness and `summary_state` would carry detector cost and failures, and re-running detectors would re-derive everything; revisit if the second read shows up in `make bench` beyond the budget). Findings in `runs.summary` JSONB (no ids, no bounds, every list pays). Read-time detection (O(events) per view, unversioned). Append-only finding versions (unbounded per run; the version column plus a rebuild is the history).

**Consequences.** Findings lag the summary by the delay (5 s default, longer for huge runs) and are visible as `processing`; one more derived table pair and one more job type; huge runs are analysed partially and say so; a rule change needs a deployment, a version bump and a bounded rebuild; findings never leak content, so there is nothing to project per role.

**Migration implications.** 0060 is additive; existing runs have no findings until re-summarized or `rebuild-findings` runs; the runtime role keeps full DML on the new tables (derived, rewritten).

**Revisit conditions.** The detect job's share of worker time exceeds the summarizer's at Stage A volumes (merge into the summarizer or move to a dedicated worker pool); a customer needs per-project thresholds (Phase 14); dismissals are requested (a `finding_dismissals` table keyed on `fingerprint`); alerts (Phase 17) need findings as triggers (the job is the natural hook).

### ADR-081: Health is a set of explained dimensions with recorded thresholds, not a score

**Context.** Spec §10.2 shows per-dimension scores and an `85/100` overall and says the score "should be explainable rather than magical"; the roadmap for Phase 10 says "explainable health dimensions only (no unexplained score)"; §80.3 requires heuristic conclusions to be labelled probable.

**Decision.** A run's health is computed at read time by a pure function over the run's derived figures and its findings: five dimensions (`reliability`, `tool_reliability`, `cost_efficiency`, `loops`, `context`), each `ok | warn | bad | no_data` with the input figures, the one-sentence rule that decided it and the finding ids involved; `overall` is the worst dimension's status as a word. No numeric score, no weights. Detector thresholds are deployment-wide settings (`ABB_FINDINGS_*`) with defaults in code; every finding records the thresholds it used in its evidence. Findings are `deterministic` (restating typed events, confidence 1.0) or `probable` (interpretations, confidence from the rule's own evidence); probable findings carry "Probable:" in their title and the UI never signals kind or severity by colour alone. A probable loop on a successful run is `info`.

**Alternatives.** A weighted 0-100 score (arbitrary weights, not actionable, contradicts the roadmap); per-project thresholds now (needs a table, write route, action, UI and audit: Phase 14); storing health on the run (a function of two derived tables; recomputation is microseconds).

**Consequences.** A reader always sees why a dimension is `bad`; comparing runs by a single number is not possible until a later phase defines one with recorded weights; tuning thresholds is an operator action that changes future findings only (past ones keep their recorded thresholds until rebuilt).
