## Decisions needed from the user (each with a recommended default)

1. **Where detectors run.** Recommended: a separate `detect_findings` outbox job enqueued by the summarizer (D1), not inside `summarize_run`. It costs one more read of the run's events per debounce window, in exchange for summary freshness and `summary_state` being untouched by detector cost or bugs, and for re-running detectors without re-summarizing.
2. **Thresholds.** Recommended: deployment-wide settings (`ABB_FINDINGS_*`, defaults in code, every threshold used is recorded in the finding's evidence). Per-project thresholds are deferred to Phase 14 (policy configuration), not built now (D6).
3. **False positives.** Recommended: no dismiss/acknowledge workflow this phase. Findings are labelled `probable` or `deterministic`, carry a stable `fingerprint` so a later dismissal table can key on it, and a successful run's loop finding is `info`, not `warning` (D7).
4. **Cost spike baseline.** Recommended: the same project and agent, the newest 200 finished runs of the previous 30 days, at least 20 of them, nearest-rank p95 (D5). Alternative: skip the cost-spike detector until analytics keep cost percentiles (it is the only detector that depends on data outside the run).
5. **Health.** Recommended: per-run dimensions (`reliability`, `tool_reliability`, `cost_efficiency`, `loops`, `context`) each `ok | warn | bad | no_data` with the inputs and the rule that produced it, and no numeric score; the spec's `85/100` example is set aside (ADR-081). Agent-level health across runs is a follow-up on the analytics rollups.
6. **UI placement.** Recommended: a "Findings" panel on the run page (health dimensions, findings with "Show evidence" jumps into the timeline) and a findings column on the runs list; no new navigation entry or page (keeps `AppShell` untouched).

## Outcome

A developer opening a run that looped, retried itself into the ground, grew its context without bound, cost far more than its siblings, failed tool after tool, or simply failed, sees *why* in words, with every claim linked to the events that prove it: "The agent repeated `search -> read -> reason` 11 times in 37 s (events 120-186)", "`db.query` failed 4 times in 9 calls, with 3 retries between", "Failed with exit code 2 from `shell` after the test suite failed; the files changed before it were ...". Deterministic conclusions are stated as facts; heuristics are labelled "probable". Findings are derived records: a job rebuilds them from the run's events (INV-2), each records the detector version that produced it (§81.2), and an operator can re-run every detector after a rule change. Nothing in a finding reveals captured content, so a VIEWER sees exactly what an OWNER sees. The product acceptance in the roadmap holds: seeded pathological runs are detected with links to evidence, detector fixtures are committed, and probable conclusions are labelled.

## Non-goals

SDK-side loop detection (the SDK keeps emitting `loop.detected` when an integration reports one; the server records it as a finding), alerts and notifications (Phase 17), findings in analytics rollups and agent-level health across runs (follow-up KI; ADR-043's tables are untouched), a dismiss/acknowledge workflow, per-project or per-agent thresholds (Phase 14), model-judged or ML root causes (§85.4), incremental summarization (KI-016 proper), time spent retrying (ADR-042), multi-agent failure chains across child runs (Phase 9 owns child-run semantics), security findings and server-side secret detection (Phase 13), evaluations (Phase 11), full-text search over findings (Phase 16), a `findings_updated` SSE frame (the run page polls the findings route while the run is active), a project-wide findings list route (the runs list carries a per-run badge). Nothing here needs Kafka, ClickHouse, Redis or Kubernetes.

## Decisions (D1..D10; ADR drafts in the appendix)

- **D1 (ADR-080) Detectors run in their own outbox job, `detect_findings`, enqueued by the summarizer.** `summarize_run` enqueues `detect_findings` with dedupe key `f"{workspace_id}:{run_id}"` (same format as `summarize_key`; job types differ so keys never collide) in the transaction that writes the summary, delayed by D3. The handler tries `pg_try_advisory_xact_lock(hashtextextended('findings:' || workspace_id || ':' || run_id, 0))` (one writer per run for findings; when another worker holds it the job re-enqueues itself coalesced and returns instead of blocking a worker slot); its writes take only the FK key-share lock on the run row, compatible with the summarizer's `FOR NO KEY UPDATE` and with ingestion, so nothing waits on a summarization. It loads the events capped (D3) **first**, then reads the run row in the same transaction (project, agent, `cost_usd`, `summary_version`, `summary.event_count`, `ordering_mode`), derives spans, and folds **status, completion and the counters from the loaded events** (the `_status_after` fold and counters of `derive_run`, cheap next to the load), so `RunFacts` and the events are one snapshot; the run row contributes only cost, project and agent, and `run_findings` records `summary_version_seen` and `event_count_seen` so a row/event mismatch is visible. Each detector call is wrapped: an exception is re-raised as `DetectorError(detector_name, event_count)` with a fixed message, `from None`, so neither `outbox_jobs.last_error` nor the dead-letter traceback can carry an attribute value. It then queries the cost baseline (D5), de-duplicates findings by fingerprint (highest severity wins) and upserts `findings` (`INSERT ... ON CONFLICT (workspace_id, run_id, fingerprint) DO UPDATE`, deleting fingerprints no longer produced) and `run_findings` (idempotent, INV-2). Detect results are therefore a function of (the event set seen, the run's cost at the time, the baseline at the time), and only the cost-spike finding depends on the last two. Rationale over "inside the summarizer" (ADR-040's choice for cost): the summary is what every list and stream shows and must stay fast and never `failed` because a heuristic threw; §72.2 names the anomaly detector a processor of its own; the roadmap says "detectors as processors over the outbox"; re-running detectors after a rule change should not re-derive spans and cost; a detector dead-letters its own job. Cost: one more event read per run per debounce window, bounded by D3 and measured by AC-11. Rejected: computing findings at read time (O(events) per page view; not versioned); a separate worker process (same image, same queue; nothing to gain yet).
- **D2 (ADR-080) Storage: `findings` (one row per finding) and `run_findings` (one row per run), both derived.** `findings (workspace_id, id, run_id, project_id, agent_slug, run_started_at, detector, detector_version, finding_type, kind, severity, confidence, start_event_id, end_event_id, evidence_event_ids, fingerprint, evidence, created_at, updated_at)`; `run_findings (workspace_id, run_id, project_id, detectors_version, summary_version_seen, ordering_mode_seen, computed_at, event_count_seen, truncated, finding_count, max_severity)`. The run owns its findings (composite FK to `runs`, `ON DELETE CASCADE` like `spans`); `project_id` and `run_started_at` are copied so a later project-level listing or rollup needs no join (ADR-043's pattern). Identity across rebuilds is `fingerprint = sha256(detector | finding_type | start_event_id | key)` where `key` is the detector's stable identity (the pattern tokens, the event type plus tool name plus payload digest, the retry scope span, the failure category, the cause plus tool name), unique per run; `id` is **derived from it** (UUIDv5 over `workspace_id:run_id:fingerprint`, presented as `fnd_...`, new `IdKind.FINDING`), so React keys, deep links and a later dismissal table are stable across rewrites, and `created_at` is first-seen (kept by the upsert) while `updated_at` moves. `evidence_event_ids` is a bounded `UUID[]` (<= 50) holding **every** event id the finding cites (start, end and the ids inside the evidence lists), validated against the loaded events, so "evidence links resolve" is one query and Phase 11's evaluations can share the column convention (see Merge notes (f)). `evidence` is a JSON object (CHECK `jsonb_typeof = 'object'`, `pg_column_size < 16384`), and the `Finding` model keeps it well under that: every client-controlled string (`tool_name`, `model`, `error_type`, pattern tokens) is truncated to 128 characters, `pattern` and `loop.pattern` to 20 tokens, lists to their bounds, and `validate_evidence` asserts the serialised size is below 15 KiB before any write, dropping the lowest-severity findings first if a run would still exceed the per-run budget; the same truncation applies to what `describe()` renders. The runtime role keeps full DML (derived tables are rewritten; `test_runtime_role.py` covers this automatically because the tables are not in `APPEND_ONLY_TABLES`). Rejected: findings inside `runs.summary` JSONB (no per-finding ids, no evidence bound, every list pays for it); appending versions instead of rewriting (unbounded growth per run; the version is on the row and the rebuild is the history).
- **D3 (ADR-080) Bounded and adaptive.** `PgEventStore.load_run(run_id, limit=None, ordering_mode=None)` gains an optional cap applied in SQL with the **full canonical key** of the mode (`ORDER BY sequence, occurred_at, received_at, event_id` or `ORDER BY occurred_at, sequence, received_at, event_id`; both run indexes lead with `(workspace_id, run_id)`, so the sort covers only the capped set), then `sort_events` as today; the mode comes from the run row and is recorded as `run_findings.ordering_mode_seen` because the row can lag the events. The summarizer's own call stays unbounded and unordered (KI-022, unchanged). The handler passes `settings.findings_max_events` (default 50,000) and records `event_count_seen` and `truncated` on `run_findings`; the API and UI say "analysed the first 50,000 of N events". The summarizer's enqueue delay is `clamp(findings_delay_seconds * max(1, event_count / 10_000), findings_delay_seconds, 60)` with `findings_delay_seconds` default 5 s, so a 30,000-event run is re-analysed at most every 15 s while it grows and once more after it ends (the summarizer always enqueues, and coalescing folds the rest; this means every cost rebuild, `POST /v1/cost/rebuild` or Phase 16's search backfill through it, also re-runs the detectors, which the runbook and `docs/RELIABILITY.md` state; the enqueue is **not** skipped on an unchanged event count because a cost rebuild changes an input of the cost-spike detector). Detectors are linear in events (sequence detection is one pass per pattern length 1..8; the identical-request hash is linear in payload bytes; the cascade window is one pass) and never copy payloads: a payload is hashed once and dropped. The 50,000-event micro-benchmark (AC-9) is the measurement; the complexity claim is reasoned until then.
- **D4 (ADR-080) Detector versioning and re-run.** Every detector is a class with `name`, `version` (semver string, `detector_version = f"{name}@{version}"` as in §81.2) and `detect(ctx) -> list[Finding]`. `DETECTORS_VERSION` (an integer, like `SUMMARY_VERSION`) is bumped whenever any detector's rules or the evidence contract change and is stored on `run_findings.detectors_version`; the findings route reports `state: outdated` when the stored version is older. `summary_version_seen` is diagnostic only (visible in the route's `state` and the runbook; a `SUMMARY_VERSION` bump by Phase 9 or 16 does not by itself mark findings outdated because status and counters come from the events, D1). Re-run: `python -m abb_api.cli rebuild-findings --workspace W [--project P] [--since T] [--limit N]` enqueues `detect_findings` for the newest runs (the `rebuild-costs` pattern, audited as `findings.rebuild` with actor `cli`); `--limit` is an argparse-validated bound of 1..10,000 (unlike `rebuild-costs`, whose 10,000 is a default; the two differ and the runbook says so). No HTTP rebuild route this phase (the one for cost exists because BILLING people change prices from the UI; a detector version only changes with a deployment).
- **D5 (ADR-080) Cost spike is the one baseline detector.** For a terminal run only (terminal by the loaded events, D1): baseline = finished runs (`SUCCESS, FAILED, TIMED_OUT, BLOCKED`) of the same workspace, project and `agent_slug`, summarised at least once (`summary_version > 0`), started before this run and within `findings_cost_spike_window_days` (30), newest 200 by `started_at` (`ix_runs_project_started`, filtered on `agent_slug`; bounded by the window), requiring at least `findings_cost_spike_min_baseline` (20). The query lives on `RunQueries` (runs module; `findings` calls it through the service, AGENTS.md module rule). An insider with `event.write` can move the baseline either way (cheap runs make the next normal run a "spike", expensive ones hide one): the impact is a false or missing probable finding, not exposure, and the evidence shows the baseline. A finding is raised when `cost_usd > p95` (nearest rank) **and** `cost_usd > 2 x median` **and** `cost_usd >= 0.01`. The evidence stores the baseline (`n`, `median_usd`, `p95_usd`, `window_days`, `newest_started_at`) so the finding is explainable and the row is self-contained; a later rebuild may legitimately differ because the baseline moved, which the ADR states. It is `probable` with confidence 0.6 (0.8 above 5 x p95).
- **D6 (ADR-081) Thresholds are deployment settings, recorded in evidence.** `Settings` gains `findings_delay_seconds` (5), `findings_max_events` (50,000), `findings_loop_min_repetitions` (3), `findings_loop_min_repetitions_single` (8, for one-token patterns), `findings_identical_min_count` (3), `findings_retry_storm_min` (5), `findings_retry_burst_window_seconds` (60), `findings_context_growth_min_delta_tokens` (4,000 added per call on average over the stretch), `findings_context_growth_factor` (2.0), `findings_context_growth_warning_tokens` (100,000), `findings_cascade_min_failures` (3), `findings_cascade_window_calls` (10), `findings_cost_spike_min_baseline` (20), `findings_cost_spike_window_days` (30), all `ABB_FINDINGS_*`, validated (`ge`). Each finding's `evidence.thresholds` lists the values it used. Per-project thresholds would need a table, a write route, an action, UI and audit: Phase 14 (policy configuration) owns that; the detector context already takes a `DetectorConfig` so only the source of the config changes then.
- **D7 (ADR-081) Probable versus deterministic, severity, and no dismissals.** `kind = deterministic` when the finding restates typed events (N retries happened; N identical calls were made; the run failed with exit code 2) with `confidence = 1.0`; `kind = probable` for interpretations (a loop, context growth, a cost spike, a heuristic cause) with `confidence` in `[0.5, 0.95]` from the rule's own evidence (for example repetitions). Severity: `info | warning | critical` per detector (table below); a `probable` loop on a run that succeeded is `info`. The UI labels probable findings "Probable" in text, never only by colour. No dismiss or acknowledge in this phase: findings are rewritten wholesale, so a dismissal needs its own table keyed on `fingerprint`, a write action and audit; the `fingerprint` exists now so that table can be added without a rebuild.
- **D8 (ADR-080) Evidence is metadata only, by construction.** Evidence values may be: event ids, span ids, `agent_id` slugs, event types, counts, durations, token counts, costs, `tool.name`, `llm.model`, `llm.provider`, `llm.error_type`, `tool.error_type`, `shell.exit_code`, `shell.risk_class`, `shell.category`, `http.status_code`, `db.operation`, `file.operation`, `test.failed`/`test.total`, `retry.attempt`, `loop.pattern` tokens (built from event types and tool names), `policy.id`, `policy.capability`, status names and the thresholds. Never: anything in `CONTENT_ATTRIBUTES`, a span name, a payload, a payload excerpt or digest (the identical-request hash is used for grouping only and is never stored or shown: a 48-bit prefix would be an equality oracle on withheld payloads and would link payloads across runs and workspaces), `test.suite` (the SDK writes a sanitised cwd into it), `run.name`, tags, run `metadata`, `retry.reason`, `policy.reason`, free-text error messages, exception messages (D1's `DetectorError`). Enforced three ways: the `Finding` model validates evidence against an explicit key allowlist per detector; a unit test runs every detector over events built from the canary world's content values and asserts none appears in any evidence or message; the route is in the registry so `test_content_withheld.py` and `test_cross_workspace.py` cover it for every actor. Consequence: no per-actor projection is needed; a VIEWER and an OWNER get identical findings bodies (AC-7). Messages (`title`, `message`) are generated at read time from the typed evidence by one `describe(finding)` in Python, so the wording lives in one place and is never stored.
- **D9 (ADR-081) Health is a set of explained dimensions, not a score.** Computed at read time from the run row, its findings **and the findings state** by a pure `health(run_facts, findings, state) -> list[Dimension]`: `reliability` (bad when the status is `FAILED | TIMED_OUT | BLOCKED`; warn when the run succeeded or is still active with `error_count > 0` or `retry_count > 0`; ok otherwise; never `no_data`, it reads the summary only), `tool_reliability` (`tool_spans_ok / tool_spans_finished`: ok >= 0.95, warn >= 0.8, bad below; `no_data` without finished tool spans), `cost_efficiency` (`retry_cost_usd / cost_usd`: ok < 0.1, warn < 0.5 or a cost-spike finding, bad >= 0.5; `no_data` when cost is 0), `loops` (none: ok; a probable loop, reported loop or identical-request finding: warn; critical: bad), `context` (by the context-growth finding's severity: `info` is ok). **The finding-based dimensions (`loops`, `context`, and the cost-spike part of `cost_efficiency`) are `no_data` unless `state.status == current`**, with the rule sentence saying why ("not analysed yet", "analysis in progress", "findings outdated: detector rules changed", "the latest analysis failed"); `reliability` and the ratio parts read the summary and never depend on the state. Each dimension returns `status`, `inputs` (the figures), `rule` (one sentence) and `finding_ids`. `overall` is the worst status, as a word (`no_data` ranks below `ok`: it never hides a `warn`). No `0-100`; nothing is weighted. Rationale: the roadmap forbids an unexplained score and the spec's example weights are arbitrary; a dimension with its inputs is what a developer can act on. Rejected: storing health on `run_findings` (it is a function of two derived tables; recomputing per read is microseconds).
- **D10 Failure chain is a finding, not a separate resource.** `failure_chain` (detector `failure-chain`) is produced for runs whose status is `FAILED | TIMED_OUT | BLOCKED` or that contain `run.failed`: the terminal event (the `run.failed` or `run.completed` with an error status that set the terminal state, else the last error event of the run), the root error event (the first event with status `error | timeout` or a `.failed` type on the terminal event's span lineage in canonical order; the terminal event itself when the lineage has none), the span lineage (the terminal event's span and its ancestors, cycle-safe like `retry_call_ids`), the errors between root and terminal on that lineage (<= 20), retries scoped to it (`retry.attempted` whose `span_id` is on the lineage, plus those whose `retry.of_event_id` names a chain event), and mutations (`file.created | modified | deleted`, `git.commit | push`; not `file.read` or `git.diff`) between the last known-good action (the last successful `tool.call | shell.command | db.query` closer before the root; the run's first event when there is none) and the terminal event (<= 50). It carries the deterministic category of §80.2 (`command_failure | external_service_failure | provider_failure | policy_termination | timeout | tool_failure | unknown`) as `kind = deterministic`; the heuristic causes of §80.3 are separate `probable_cause` findings (D7) so each carries its own confidence. The UI renders the chain as an ordered list of linked events. Rejected: a `/failure-graph` route and a graph model (nothing consumes a graph yet; the chain is the §80.1 list, which the finding contract already expresses).

### Detectors (all pure; `detect(ctx: DetectorContext) -> list[Finding]`; `ctx` holds canonically ordered events, derived spans, `RunFacts` folded from those events plus cost/project/agent from the run row, the cost baseline and `DetectorConfig`)

Two rules apply to every detector. **Per emitter**: token streams, series and windows are partitioned by `event.agent_id` (Phase 9 interleaves several emitters in one run; a merged stream would hide or invent patterns), and findings report `agent_id` in evidence (a slug, metadata). **Time windows** ("within 60 s") are measured on `occurred_at` of the events in canonical order; under clock skew between emitters they are best effort (KI-095), and the shuffle test cannot catch this, so a skewed two-emitter fixture is part of AC-1.

| Detector (`name@version`) | Rule (defaults from D6) | Kind, severity, confidence | Evidence keys |
| --- | --- | --- | --- |
| `repeated-sequence@1.0.0`, type `possible_loop` | Tokens from closers and point events in canonical order: `tool.call.* -> tool:<tool.name>`, `llm.request.* -> llm`, `shell.command.* -> shell`, `db.query.* -> db`, `file.<op>`, `git.<x>`, `http.response -> http`. For pattern length n in 1..8, find the longest run of consecutive repetitions; report when repetitions >= 3 (n >= 2) or >= 8 (n = 1: the same tool again and again, the commonest loop, which `identical-request` only sees with captured payloads) and the repeated block covers >= 6 tokens; choose the shortest n with maximal coverage; at most one finding per disjoint stretch, 50 per run. | probable; `info` if the run succeeded and repetitions < 6, `warning` otherwise, `critical` at >= 10; confidence `min(0.95, 0.5 + 0.05 x repetitions)` | `agent_id`, `pattern` (<= 20 tokens of <= 128 chars), `repetitions`, `event_ids` (first of each repetition, <= 50), `start_event_id`, `end_event_id`, `duration_ms`, `thresholds` |
| `identical-request@1.0.0`, type `identical_request` | For `tool.call.started` and `llm.request.started` **with an inline payload**: `sha256(canonical JSON of payload)` groups events by `(agent_id, event_type, tool.name, digest)`; report groups with count >= 3. The digest is the grouping key and part of the fingerprint input only; it is never stored or shown. Without payloads the detector reports nothing (capture is opt-in, INV-5; the absence is not a finding). | deterministic, `warning`, 1.0 | `agent_id`, `event_type`, `tool_name` (tool calls only), `count`, `event_ids` (<= 50), `thresholds` |
| `retry-storm@1.0.0`, type `retry_storm` | Burst rule: >= 3 `retry.attempted` with the same `span_id` within 60 s of `occurred_at`. Absolute rule: >= 5 retries in the run. | deterministic, 1.0; `warning` when the burst rule fires (>= 15 retries: `critical`), `info` when only the absolute rule fires (five spaced retries in a three-hour run are not a storm) | `agent_id`, `retries`, `retries_unattributed`, `burst` (bool), `by_scope` ([{`span_id`, `count`, `first_event_id`, `last_event_id`}] <= 20), `rate_limit_hits`, `window_seconds`, `thresholds` |
| `context-growth@1.0.0`, type `context_growth` | `llm.input_tokens` of `llm.request.completed` per emitter in canonical order (§81.1: "grows monotonically beyond configured rate", a rate, not a ratio: ordinary multi-turn agents grow linearly by construction). A non-decreasing stretch of >= 5 calls is reported when **both** the mean increment over the stretch >= 4,000 tokens per call and the last value >= 2.0 x the first, **and** either the increments themselves increase over the stretch (super-linear: the context compounds) or the last value >= 100,000 tokens. | probable, confidence 0.7 (0.85 at >= 10 calls); `info` below 100,000 tokens, `warning` at >= 100,000, `critical` at >= 150,000 | `agent_id`, `calls`, `first_tokens`, `last_tokens`, `growth_factor`, `mean_delta_tokens`, `superlinear` (bool), `series` ([{`event_id`, `input_tokens`}] <= 50, sampled evenly), `start_event_id`, `end_event_id`, `thresholds` |
| `cost-spike@1.0.0`, type `cost_spike` | D5. Terminal runs only. | probable, `warning` / `critical` above 5 x p95, 0.6 / 0.8 | `cost_usd`, `baseline` {`n`, `median_usd`, `p95_usd`, `window_days`, `newest_started_at`, `agent_slug`}, `thresholds` |
| `tool-failure-cascade@1.0.0`, type `tool_failure_cascade` | Over closers of `tool.call | shell.command | db.query` and `http.response` with status >= 500: a sliding window of 10 such calls (per emitter) containing >= 3 failures (`.failed`, or status `error|timeout`); merged into one stretch per overlap; <= 50 per run. | deterministic, `warning`, `critical` if the run failed, 1.0 | `agent_id`, `failures` ([{`event_id`, `event_type`, `tool_name`, `error_type`, `exit_code`, `status_code`}] <= 20), `calls_in_window`, `retries_between`, `alternates` (tool names used after a failure, <= 10), `start_event_id`, `end_event_id`, `thresholds` |
| `failure-chain@1.0.0`, type `failure_chain` | D10. | deterministic, `critical` if the run failed else `warning`, 1.0 | `category`, `terminal_event_id`, `root_event_id`, `chain` ([{`event_id`, `event_type`, `role`: `terminal|root|error|retry|mutation`, `span_id`}] <= 50), `span_lineage` (<= 20), `retries_caused`, `retries_unattributed`, `mutations` (count) |
| `failure-chain@1.0.0`, type `probable_cause` | §80.3: `code_change_before_test_failure` (a `file.modified|created` precedes a `shell.command.*` with `test.failed > 0` inside the chain), `repeated_tool_timeout` (>= 2 `timeout` statuses or `timeout.occurred` on one `tool.name`), `context_overflow` (`llm.request.failed` whose `llm.error_type`, lower-cased and split on non-letters, contains one of the whole words `context_length`, `context_window`, `max_tokens`, `too_long`, `prompt_too_long`, `content_too_large`; never a bare `token`, which would match `invalid_token`), `invalid_tool_arguments` (`tool.error_type` whole words `invalid_argument(s)`, `validation_error`, `schema_error`, `invalid_param(s)`). | probable, `warning`, 0.5-0.7 | `cause`, `event_ids` (<= 20), `tool_name` / `model` where relevant |
| `reported-loop@1.0.0`, type `reported_loop` | Each `loop.detected` event (an integration said so). | deterministic, `warning`, 1.0 | `pattern` (`loop.pattern`), `repetitions`, `event_id` |

Every detector is arrival-order-independent (it sorts nothing itself; the context is canonically ordered once; windows follow the rule above) and tolerant of hostile attributes (a missing or wrongly typed value is skipped, never raised on: NaN/inf/negative token counts, a string `shell.exit_code`, a 4,096-character `tool.name`, a 64-item `loop.pattern`). A detector *bug* (an exception) is not swallowed: it is re-raised as `DetectorError` with a fixed message (D1), the job fails and retries like any handler and dead-letters after five attempts, which the route reports as `state: failed`; a bug must surface, and the summary is unaffected. `run_all` de-duplicates by fingerprint (highest severity wins) so a detector's duplicate can never trip the unique index into a dead letter. One incident can still yield several findings (`retry_storm` + `tool_failure_cascade` + `failure_chain` + `probable_cause`); the badge counts them all this phase (KI-093).

### Fixtures and seeds (the "seeded pathological runs" and "detector fixtures" of the roadmap)

- `scripts/pathological_runs.py` (stdlib + `httpx`, run from `apps/api`): deterministic generator (fixed ids from a seed, fixed timestamps) of ten runs: `healthy` (a normal coding run **with an ordinary monotonic context, 8k -> 24k input tokens over 8 calls**, two spaced retries, one tool failure: exercises every detector's negative side), `looping` (search/read/reason x 11, plus a stretch of `tool:read` x 9 for the single-token rule), `identical` (one tool called 7 times with the same inline payload), `retry_storm` (9 retries, 4 on one span within 20 s), `context_growth` (7 model calls 8k -> 120k input tokens with increasing increments), `two_agents` (two emitters interleaved: agent A loops search/read x 6 while agent B does plan/write; only A's loop is reported, with `agent_id`), `skewed` (two emitters whose `occurred_at` clocks differ by 5 minutes: retry bursts are judged per emitter and the fixture documents the best-effort window), `cost_spike` (25 baseline runs of ~$0.02 for agent `spiky` and one of $0.90; the baseline runs are real runs with real model-call events so the cost engine prices them), `cascade` (db.query fails 4 times in 9 calls with 3 retries, then a different tool), `failing` (file.modified -> test command exit 1 -> retry -> shell exit 2 -> run.failed). Modes: `--out DIR` writes `<name>.ndjson` (one wire event per line), `--api URL --key K` posts them in batches (shuffled per batch with `--shuffle SEED` to exercise arrival order), `--check DIR` exits 1 if regenerating differs from the files.

## Security review note (mandatory adversarial pass)

Scenarios the reviewer must attempt (expected result in parentheses):

1. Content through evidence: ingest a run whose `shell.command`, `shell.cwd`, `file.path`, `git.repo`, `http.url`, `test.failing`, `span.name`, `run.name`, tags, run `metadata`, `retry.reason`, `policy.reason` and payloads contain canaries; read findings as every actor (no canary anywhere, including `title`/`message`, for OWNER too); a `custom.*` event with a `thing.command` attribute (never copied: evidence keys are an allowlist, not a denylist).
2. Hash oracle: the identical-request payload digest appears nowhere (not in `evidence`, `evidence_event_ids`, `fingerprint` as exposed, titles, logs or `last_error`); a reviewer confirms by grepping the response and the tables for any hex run of 12 or more characters that is not an id. The `fingerprint` is a digest over detector, type, start id and the key: for identical requests the key includes the payload digest, so the reviewer also confirms the fingerprint cannot be inverted to the digest (it is a hash of a hash with other inputs) and that no actor can supply a candidate payload to compare against it.
3. Tenant isolation: findings for a foreign or random run id (404, identical body); the cost baseline for an agent slug that exists in both tenants (counts only the caller's workspace; test with the canary tenant's 777.777 runs); `rebuild-findings --workspace` for a workspace the CLI user names (CLI is trusted; the audit row names the workspace); an insider with `event.write` moving the baseline (a false or missing probable finding, not exposure).
4. Authorization: BILLING (403 `PERMISSION_DENIED`), a key without `runs:read` (403 `INSUFFICIENT_SCOPE` with `required_scope: runs:read`), HEAD/OPTIONS, a removed member mid-poll (401/404 as for runs), a project-bound key for a run of another project (404).
5. Resource exhaustion: a run engineered to produce thousands of candidate findings (50 per detector, 200 per run, evidence under 15 KiB by the model, 16 KiB by CHECK, ids lists of 50); a 60,000-event run (cap, truncation flag); 1,000 events in one second for one run (coalescing: one job per delay window; the adaptive delay grows); a run whose events have 4 KiB attribute strings and 64 KiB payloads each (hashed, never copied); a `loop.pattern` list of 64 entries of 4,096 characters (evidence stores at most 20 tokens, each truncated to 128 characters); a `tool.name` of 4,096 characters (truncated to 128 in evidence, like rollup names); two findings with the same fingerprint from one detector (one row, no dead letter).
6. Job isolation: a detector that raises (its job dead-letters after 5 attempts with the fixed `DetectorError` message; `summary_state` stays `current`; the findings route says `failed` and still returns the previous analysis with its time); a job for a deleted or unknown run (no-op); a job that outlives its lease (heartbeat; the try-lock makes the second worker re-enqueue, never double-write); a job whose run row lags the events (status from the events, `summary_version_seen` recorded).
7. Logs and the outbox: no evidence, payload, attribute value, exception text or message in any log line or in `outbox_jobs.last_error` (structured logs carry `run_id`, `detector`, counts and `duration_ms` only); the log-hygiene pattern of `test_ingestion_api.py` extended to the job, including a detector raising with the canary in its message.
8. Determinism: two rebuilds of the same run give the same fingerprints; a changed `DETECTORS_VERSION` without a rebuild shows `outdated`, never stale findings presented as current.
9. UI: evidence strings render as text (no HTML); the "Show evidence" jump for an event id that is not in the loaded events (filtered or not yet paged) fails soft (no crash, a notice); a finding with 50 chain entries does not blow the layout on mobile.
10. Bounds on inputs to the detectors: NaN/inf/negative token counts, `shell.exit_code` as a string, `occurred_at` ties, cyclic `parent_span_id` (the chain's lineage walk is cycle-safe like `retry_call_ids`), events of two agents in one run (partitioned per `agent_id`: no cross-emitter pattern, no cross-emitter window).

## Risks

1. **False positives on legitimately repetitive agents** (a loop over 20 files looks like `read -> edit -> test` x 20). Mitigation: `probable` with "Probable:" in the title, `info` on successful runs, repetitions and duration in the evidence, thresholds configurable per deployment; the identical-request detector (payload hashes) is the deterministic companion that distinguishes a true loop. Dismissals are a named follow-up keyed on `fingerprint`.
2. **Worker cost on huge runs** (a second full event read per run; KI-016 tail). Mitigation: the cap, the adaptive delay, the `make bench` gate (AC-11) with a stated budget and a tuning loop; the summarizer path is unchanged.
3. **Content leakage through evidence or messages.** Mitigation: allowlisted evidence keys per finding type, canary tests over every actor, no per-actor projection to get wrong, review scenario 1.
4. **Merge conflicts with Phases 9, 11 and 16.** Mitigation: the "Merge notes" below; no change to the matrix, actions, `AppShell`, `quality.sh` or `runs/summary.py`; generated artifacts regenerated in the last commit of the step that changes them; the CSS block is appended.
5. **Tautological fixtures** (expected findings written from the detector's output). Mitigation: `*.expected.json` is hand-written from the scenario description before the detector runs, reviewed in the PR, and the mutation checks (a threshold change must break a fixture).
6. **Cost-spike noise** (small baselines, cheap runs). Mitigation: D5's three conditions and the minimum baseline; the evidence shows the baseline so a reader can judge; the detector can be switched off by `ABB_FINDINGS_COST_SPIKE_MIN_BASELINE` above any plausible count (documented).
7. **Schema drift between the finding model and the UI.** Mitigation: `FindingOut.evidence` is typed per `finding_type` in OpenAPI (a discriminated union would be ideal; a documented `dict` with per-type keys in `api-v1.md` is the minimum), the web types regenerated, the fixtures reuse the Python-generated expected JSON where possible.
8. **Flaky E2E timing** (findings arrive after a job delay). Mitigation: the script sets both delays to 0 and polls `state.status` with a bound, as `analytics-e2e.sh` does for rollups.
9. **Client-controlled sizes reaching the database CHECK** (a dead letter any `event.write` key can cause). Mitigation: truncation and the size assertion live in the `Finding` model and are unit-tested with the schema's maximum attribute sizes (AC-2); the CHECK is a backstop.
10. **Health that looks fine before anything ran.** Mitigation: finding-based dimensions are `no_data` unless the analysis is `current`, with the reason in the rule (AC-6).
11. **Benchmark noise read as regression or as a pass.** Mitigation: medians of three before and three after in one session, the detect job's own `duration_ms` as the primary measure, raw triples recorded (AC-11).

## Appendix: ADR drafts (written at step 7 as `docs/decisions/ADR-080-*.md` and `ADR-081-*.md`; the files are authoritative)

### ADR-080: Findings are derived, versioned, metadata-only records produced by a bounded detector processor over the outbox

**Context.** Spec §81 asks for deterministic detectors over windows of events with a versioned finding contract (§81.2: type, severity, confidence, start/end event ids, evidence, detector version) and §80 for an evidence-based failure analysis; §72.2 lists the anomaly detector as a processor; INV-2 requires derived state to be rebuildable; ADR-061 withholds captured content from actors without `payload.read`; KI-016/022 make any new per-run pass over events a cost to bound.

**Decision.** (1) A `detect_findings` outbox job, enqueued by `summarize_run` in its transaction (dedupe per run, delay growing with the run's event count, capped at 60 s), loads at most `ABB_FINDINGS_MAX_EVENTS` events by the run's full canonical order key, then reads the run row in the same transaction (cost, project, agent, versions), derives spans, folds status and counters from the loaded events (so facts and events are one snapshot), runs every detector as a pure function per emitter (`agent_id`), and upserts `findings` and `run_findings` for the run by fingerprint under a per-run try-advisory-lock (one writer; the loser re-enqueues; writes take only the FK key-share on the run row, compatible with the summarizer's `FOR NO KEY UPDATE`, the pattern of `analytics/rollup.py`). The summarizer, `summary_state` and the stream are untouched; a detector exception is re-raised as a fixed-message `DetectorError` so neither the outbox's `last_error` nor the dead-letter log can carry an attribute value, and it dead-letters its own job. Detect results are a function of (the event set seen, the run's cost at the time, the cost baseline at the time); only the cost-spike finding depends on the last two. (2) Findings are rows keyed by the run (composite tenant key, cascade), with `detector_version` (`name@semver`), `kind` (`deterministic | probable`), `severity`, `confidence`, `start_event_id`/`end_event_id`, `evidence_event_ids uuid[]` (every cited event id, <= 50, validated against the run), a stable `fingerprint` (`sha256(detector | type | start_event_id | key)`; a late-arriving earlier event can extend a stretch backwards and change it, so a future dismissal design must not assume stability under late arrival), an `id` derived from the fingerprint (UUIDv5, `fnd_` prefix; stable across rewrites; `created_at` is first-seen), and a bounded JSON `evidence`; `run_findings` records `detectors_version`, `summary_version_seen`, `ordering_mode_seen`, `event_count_seen` and `truncated`. A bump of `DETECTORS_VERSION` marks stored findings `outdated`; `rebuild-findings` re-derives (bounded, audited); after a dead letter the previous analysis stays readable, marked `failed` with its time. (3) Evidence is metadata by construction: an allowlist of keys per finding type (ids, agent slugs, types, counts, tool and model names, exit and status codes, thresholds); never a content attribute, span name, payload or payload digest (the identical-request hash groups events and is never stored or shown), `test.suite`, run name, tag, metadata, free-text reason or exception text. Titles and messages are generated at read time from the typed evidence. Consequently the route needs no per-actor projection and a VIEWER sees what an OWNER sees. (4) The cost-spike detector is the one that reads beyond the run (a bounded baseline of the same agent's recent summarised finished runs, queried in the runs module); its evidence stores the baseline, a rebuild may differ when the baseline has moved, and an insider can move it (a false or missing probable finding, not exposure). (5) Bounds are a rule of the `Finding` model, not of the database: 50 findings per detector, 200 per run (lowest severity dropped first), 50 ids per list, 20 pattern tokens, every client-controlled string truncated to 128 characters, serialised evidence under 15 KiB (the 16 KiB CHECK is the backstop), duplicates by fingerprint collapsed before any write. (6) Every cost rebuild also re-runs the detectors; the enqueue is not skipped on an unchanged event count because a cost rebuild changes a cost-spike input.

**Alternatives.** Detectors inside `summarize_run` (one snapshot, no second read; rejected because summary freshness and `summary_state` would carry detector cost and failures, and re-running detectors would re-derive everything; revisit if the second read shows up in `make bench` beyond the budget). Findings in `runs.summary` JSONB (no ids, no bounds, every list pays). Read-time detection (O(events) per view, unversioned). Append-only finding versions (unbounded per run; the version column plus a rebuild is the history).

**Consequences.** Findings lag the summary by the delay (5 s default, longer for huge runs) and are visible as `processing`; one more derived table pair and one more job type; huge runs are analysed partially and say so; a rule change needs a deployment, a version bump and a bounded rebuild; findings never leak content, so there is nothing to project per role.

**Migration implications.** 0060 is additive; existing runs have no findings until re-summarized or `rebuild-findings` runs; the runtime role keeps full DML on the new tables (derived, rewritten).

**Revisit conditions.** The detect job's share of worker time exceeds the summarizer's at Stage A volumes (merge into the summarizer or move to a dedicated worker pool); a customer needs per-project thresholds (Phase 14); dismissals are requested (a `finding_dismissals` table keyed on `fingerprint`); alerts (Phase 17) need findings as triggers (the job is the natural hook).

### ADR-081: Health is a set of explained dimensions with recorded thresholds, not a score

**Context.** Spec §10.2 shows per-dimension scores and an `85/100` overall and says the score "should be explainable rather than magical"; the roadmap for Phase 10 says "explainable health dimensions only (no unexplained score)"; §80.3 requires heuristic conclusions to be labelled probable.

**Decision.** A run's health is computed at read time by a pure function over the run's derived figures, its findings and the findings state: five dimensions (`reliability`, `tool_reliability`, `cost_efficiency`, `loops`, `context`), each `ok | warn | bad | no_data` with the input figures, the one-sentence rule that decided it and the finding ids involved; the finding-based dimensions are `no_data` (with the reason) unless the analysis is `current`, so a run analysed by no detector, by outdated rules or whose latest analysis failed never reads `ok`; `overall` is the worst dimension's status as a word and `no_data` never masks a `warn`. No numeric score, no weights. Detector thresholds are deployment-wide settings (`ABB_FINDINGS_*`) with defaults in code; every finding records the thresholds it used in its evidence. Rules are rates and absolute sizes rather than ratios where a ratio would flag ordinary behaviour: context growth is reported on the increment per call and on super-linear growth or an absolute size, because a multi-turn agent's context is non-decreasing by construction; five spaced retries are `info`, a burst is `warning`. Findings are `deterministic` (restating typed events, confidence 1.0) or `probable` (interpretations, confidence from the rule's own evidence); probable findings carry "Probable:" in their title and the UI never signals kind or severity by colour alone. A probable loop on a successful run is `info`, and the UI says that severity may change until the run ends.

**Alternatives.** A weighted 0-100 score (arbitrary weights, not actionable, contradicts the roadmap); per-project thresholds now (needs a table, write route, action, UI and audit: Phase 14); storing health on the run (a function of two derived tables; recomputation is microseconds).

**Consequences.** A reader always sees why a dimension is `bad`; comparing runs by a single number is not possible until a later phase defines one with recorded weights; tuning thresholds is an operator action that changes future findings only (past ones keep their recorded thresholds until rebuilt).
