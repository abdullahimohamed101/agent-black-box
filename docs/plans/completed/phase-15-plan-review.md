# Independent review of the Phase 15 plan (auth, workspaces, RBAC)

Reviewed: `docs/plans/active/phase-15-auth-rbac.md` at commit f54c2d1, against the code on `feature/phase-15-auth-rbac`
(main 85d4121, migrations head 0044). Reviewer stance: adversarial, plan-only; no code, tests or migrations were changed.
The four user decisions (generic OIDC with a fake provider, invite-only, VIEWER metadata-only, BILLING writes prices) are
taken as given; only their safe implementation is reviewed.

Severity: **P0** critical (do not start), **P1** must fix in the plan before implementation, **P2** should fix (can be a
step-level note), **P3** optional. Every finding cites the plan line (`plan:L<n>`) or a file:line.

Summary: no P0. Nine P1 findings, all fixable by editing the plan text before step 1. The plan's reading of the current
code is accurate on every load-bearing claim I could check (section A), and the architecture (one `Principal`, one
`require(action)`, matrix as data, fail-closed registry, canary) is the right shape. The gaps are in the details that make
such designs leak in practice: an SDK key that can list members' emails, email-based account linking that can take over
an already-linked user, a login rate limiter keyed in a way that lets one attacker lock everyone out, a dev/test switch
that is open by default, an append-only audit table that a VIEWER can grow without bound, and some unwritten OIDC
binding rules.

## B. Authorization holes by design

- **B-1 (P1) plan:L168 `member.read` is granted to "any scope (project keys: own project)".** A project-bound `events:write` key embedded in a customer's agent process can call `GET /v1/members` and read every member's email and role of the workspace. Spec §92: "SDK keys should not be able to administer a workspace"; §90.1 lists user identity as an asset; §93 member emails are at least Class 1. Attack: an agent key leaks from a CI log (the usual way), the attacker enumerates the organisation's dashboard users and roles (who is OWNER) and phishes the invitation flow. Correction: keys get `workspace.read` and `project.read` only; `member.read`, `invite.*`, `audit.read`, `api_key.read` are session-only. Also state what `workspace.read` returns to a project key (its own workspace row, nothing else).
- **B-2 (P1) plan:L172-173 and L203: "bearer only" routes are enforced by the matrix, but the matrix also gives sessions `run.write`-adjacent surface via `POST /v1/projects`.** Not a hole by itself, but `project.write` with no bound (plan:L87 bounds members, keys, invitations; projects are unbounded) contradicts plan:L86 "Phase 15 adds no client-controlled unbounded cardinality". An ADMIN can create projects until the rollup tables (bounded per project, KI-055) and `projects` grow without limit. Correction: bound projects per workspace (e.g. 200, `409`), listed with the other bounds. (P2 if you consider admins trusted; P1 because the plan makes an explicit claim that is false.)
- **B-3 (P1) plan:L150-151 invitations: acceptance can downgrade or remove an OWNER and bypasses `member.write_owner`.** "Accepting ... creates/updates the membership." An ADMIN (no `member.write_owner`) invites an existing OWNER's email with role VIEWER; if the OWNER clicks the link, their membership is updated to VIEWER, possibly leaving zero owners. Correction: on accept, if a membership exists, either (a) refuse (`409 ALREADY_MEMBER`) or (b) apply the same rules as `PATCH /v1/members`: touching a current OWNER requires the inviter to have held `member.write_owner` at invitation time **and** the last-owner rule is evaluated at acceptance time under the same lock as B-4. State which.
- **B-4 (P2) plan:L153 last-owner rule needs a lock.** Two concurrent `DELETE /v1/members/{a}` and `/{b}` of the only two owners both see "another owner exists" and both succeed. Correction: the check and the write run in one transaction with `SELECT ... FROM workspace_members WHERE workspace_id = ? AND role = 'OWNER' FOR UPDATE` (or a `pg_advisory_xact_lock` on the workspace id). Add a concurrency test.
- **B-5 (P2) plan:L179 `member.write_owner` must also cover demotion and removal of a current OWNER, and self-changes.** The table says "grant/revoke OWNER"; an ADMIN with `member.write` could otherwise `PATCH` an OWNER to VIEWER or `DELETE` an OWNER. Correction: define `member.write_owner` as "any change to a membership whose current or new role is OWNER". Also decide and test: may a member change or remove their own membership (an OWNER demoting themselves while another owner exists is fine; an ADMIN removing themselves is fine; a DEVELOPER cannot touch members at all).
- **B-6 (P2) plan:L196-197, L261: `GET /v1/invitations` has no action in the matrix and its response shape is unspecified.** It lists invitee emails, inviter and role; the token must never appear (only `token_hash` is stored, so the response cannot leak it unless the create response is echoed). Correction: `GET /v1/invitations` and `DELETE /v1/invitations/{id}` need `invite.write` (or a new `invite.read` for OWNER/ADMIN only); the OpenAPI schema for `InvitationOut` has no `token` field and only `POST /v1/invitations` returns `invite_url` once. Add to AC-7.
- **B-7 (P2) plan:L151 the invitation token travels in the URL path `/invite/<token>`.** It lands in the inviter's clipboard history, the invitee's browser history, the Next server's access logs (a path), and any reverse proxy log. `Referrer-Policy: no-referrer` (next.config.ts) covers the Referer, not logs. Correction: put the token in the fragment (`/invite#<token>`; the page reads `location.hash` and POSTs it) or accept the path form but have the `/invite/[token]` page immediately `history.replaceState` and never log the path; the plan's log-hygiene scenario (plan:L328) must include the web server's access log, not just the API's.
- **B-8 (P2) plan:L135 `X-ABB-Workspace` semantics for `/v1/invitations/accept`.** The route is "without a workspace" (plan:L136), so the server must take the workspace from the invitation row and must reject a header that names a different workspace (else a client-side mix-up silently accepts into the wrong tenant). State it. Also: the user's `email_verified` email must equal the invitation email *at acceptance time* (not only at login), so a user who changes IdP email cannot accept an old invitation addressed to someone else.
- **B-9 (P3) plan:L142 `GET /v1/artifacts/{id}/content` 403 for VIEWER: order the checks.** If visibility is looked up first, a VIEWER gets `403` for an existing artifact and `404` for a missing one within their own workspace (harmless; metadata is readable anyway) but the behaviour must be the same for foreign ids (`404`). Correction: `require("payload.read")` before any lookup, so a VIEWER gets `403` for every id and the cross-workspace test still sees `404` only for actors who hold the permission.
- **B-10 (P3) plan:L168 VIEWER and BILLING see every member's email.** A product choice; note it in SECURITY.md ("members list is visible to all roles") so it is deliberate.
- **B-11 (P3) plan:L140 `runs:read` implies `payload.read` for keys (compatibility).** Fine, but then a DEVELOPER (who holds `payload.read`) is the lowest role that can mint a key; SECURITY cannot create keys but can revoke any. OK. Make the key-creation rule explicit: a user may only create a key whose implied actions are a subset of their own (today that is trivially true for every role with `api_key.create`; the rule prevents a future BILLING/`api_key.create` combination from minting `runs:read`).
- **B-12 (P3) plan:L125 `actor_id = user:<usr_id>` is the stream-limit key but plan:L326 item 9 expects limits "scoped to that session, other sessions unaffected", and plan:L80 says "per-session stream limits".** Contradiction. Decide: per user (10 streams across all tabs/devices; simpler) or per session (`session:<id>`). The test must match.
- **B-13 (P3) `GET /v1/me` and the dual-member canary (plan:L262-263).** A user who is a member of both tenants legitimately sees globex's slug and name in `/v1/me`; the rule "no response body to an acme actor may contain the canary, including `/v1/me`" only holds because workspace name/slug are not canary-marked. Say so explicitly, and mark the globex *project* names, not the workspace, so the test cannot be weakened by accident.

Verified correct in the design (no finding): foreign ids are 404 with identical bodies today (`runs/service.py:272-284`, `artifacts/service.py:198-205`, `projects/access.py`), which the plan keeps; health endpoints carry no tenant data (`health/router.py`); `/v1/me` and `/v1/auth/*` are the only workspace-less user routes; `authorize()` runs before body reads for ingestion routes because `require` is a dependency; `Own(api_key.revoke)` cannot cross tenants because `ApiKeyRepository.revoke` is tenant-scoped (`auth/repository.py:151-162`).

## C. OIDC and session design

- **C-1 (P1) plan:L111-112 email-based linking can take over an already-linked account.** "identity is matched first by `(provider, subject)`, then by verified lower-cased email to link a user who was pre-provisioned". If the email fallback also applies to a user whose `provider_subject` is already set (a different subject at the same provider, or any subject after the operator changes `ABB_OIDC_ISSUER`), then whoever can obtain a verified token for that email at the configured IdP becomes that user. With Keycloak/Auth0/self-hosted providers, "verified" is whatever the IdP admin says, and some tenants allow users to add a verified alias. Correction: the email fallback applies **only** when `users.provider_subject IS NULL`; a verified email that matches a user with a different `(provider, subject)` is refused (`401`, logged `identity_conflict`, no row changed). Re-linking after an issuer change is an explicit CLI command (`relink-user --email --clear-subject`), audited. Add the negative test to AC-5.
- **C-2 (P1) plan:L107-108 the callback must bind the query `state` to the `abb_login` cookie, not only look it up.** The text says the row is "referenced by a short-lived `abb_login` cookie carrying `state`" but the verification rule is not written. If the callback only looks up `sha256(query.state)` in `login_states`, a login-CSRF works: the attacker starts a login, stops at the IdP callback, and sends the victim `/api/auth/callback?code=...&state=...`; the victim is signed in as the attacker (and `return_to` is attacker-chosen within the allowed set), which lets the attacker later read whatever the victim does in that session in their own tenant. Correction: the callback requires `cookie.abb_login == query.state` (constant-time), deletes the row and clears the cookie on every outcome, and the `abb_login` cookie is `HttpOnly; SameSite=Lax; Path=/api/auth` (Lax, not Strict: the IdP redirect is a top-level cross-site GET and must carry it). Add "state in query but cookie absent or different -> 400, no session" to the AC-5 negatives.
- **C-3 (P1) plan:L90-91, L215 the login rate limiter key is undefined and the API never sees the client IP.** Every login reaches the API through the Next relay, so the API sees one source address. A per-process `InMemoryRateLimiter` keyed by "IP" would either (a) throttle all users together, so one attacker looping `GET /v1/auth/login` locks everyone out of login, or (b) key on an `X-Forwarded-For` the API has no rule to trust, which the attacker sets freely through the proxy (`upstream.ts` forwards nothing today, but the plan adds header forwarding). Correction: define it. Simplest safe option: the limit lives in the Next route handlers (`/api/auth/login`, `/api/auth/callback`) keyed by the client address Next sees (behind its own trusted proxy config), plus a *global* bucket on the API as a backstop sized so it cannot be exhausted by one client at the Next limit. State that the API ignores `X-Forwarded-For` unless `ABB_TRUSTED_PROXY_CIDRS` is set, and that the proxy strips any client-supplied `X-Forwarded-*`/`Forwarded` before forwarding.
- **C-4 (P1) `ABB_ENVIRONMENT` defaults to `development` (`core/config.py:17`), and several unsafe features are gated on "not production" (plan:L159 `create-session`, L119 `http://` issuer "unless development or test", L329 fake provider).** A deployment that forgets to set the variable is "development", and the shipped `docker-compose.yml:5` and `.env.example:2` both set `ABB_ENVIRONMENT=development` explicitly, so the first real deployment copied from them is too. In that state: `create-session` mints a session for any email with no IdP, an `http://` issuer (a fake provider) is accepted, and `seed` creates an OWNER membership for `owner@local.test`. Correction: gate on `environment in {"development", "test"}` everywhere (never "!= production"), and have the API log a WARNING at startup when OIDC is configured and `environment != production`. Better: make `create-session` additionally require `ABB_ALLOW_DEV_SESSIONS=1` so an accidental dev-mode production still cannot mint sessions. Document in the runbook that `ABB_ENVIRONMENT=production` is mandatory.
- **C-5 (P2) plan:L110 JWKS caching, rotation and failure modes are unspecified.** Without a rule, either every login fetches the JWKS (an IdP outage or a slow JWKS endpoint becomes a login outage with a 5 s timeout per attempt, times the rate-limit budget), or keys are cached forever (rotation breaks login until restart). Correction: cache the JWKS per issuer with a TTL (e.g. 1 h), refetch on an unknown `kid` at most once per 60 s (bounded), reject a token whose `kid` is still unknown after that, and never accept a key embedded in the token (`jku`/`jwk` headers ignored). State that `algorithms=["RS256","ES256"]` is passed explicitly to `pyjwt` (no `none`, no HS*). `pyjwt`'s `PyJWKClient` has a cache; say whether it is used or wrapped so the test clock controls it.
- **C-6 (P2) plan:L110 verify the discovery document's `issuer` equals `ABB_OIDC_ISSUER` and that `token_endpoint`/`jwks_uri` are `https` and under the issuer's host (or an allowlist).** OIDC Discovery requires the first; the second limits the blast radius of a compromised or mis-typed discovery URL (the API would otherwise POST the client secret and the code to whatever host the document names). Also pin `aud` to the client id and, if `azp` is present, require it to equal the client id.
- **C-7 (P2) plan:L109 the `return_to` rule "starts with `/` and not `//`" does not cover `/\evil` (plan:L319 lists it as a test, but the rule as written accepts it), `/%2F%2Fevil`, or paths with CR/LF.** Correction: allow only `^/(w|invite)(/[A-Za-z0-9._~-]+)*/?(\?[A-Za-z0-9=&._~%-]*)?$`-style paths (an allowlist of the app's own routes), reject anything containing `\`, `%`, control characters or `@`; store it only after validation; the callback redirects via a 302 with the validated string, never via a user-controlled `Location` fragment.
- **C-8 (P2) plan:L113 `email_verified` must be true: define the behaviour when the claim is absent.** Entra ID and some Okta configurations do not emit `email_verified`; the plan's rule makes every login fail with no explanation. Correction: absent claim -> refuse (fail closed) **and** log `email_verified_missing` with the provider, and document the setting an operator would need (a later `ABB_OIDC_TRUST_EMAIL=1`, not in this phase). AC-14 (the manual real-provider login) should record which claims the provider sent.
- **C-9 (P2) plan:L105, L217 cookie and CSRF details.** (a) Use the `__Host-` prefix when `Secure` is on (`__Host-abb_session`): it pins `Path=/`, forbids `Domain`, and cannot be overwritten by a subdomain; the name can differ between http dev and https prod via one constant. (b) `SameSite=Lax` is right for the session; note that `Lax` still sends the cookie on cross-site top-level GETs, so **no GET route may have side effects**: `/v1/auth/logout` must be `POST` (the plan does not say which method; `GET /logout` is a classic CSRF logout). (c) The `Origin` check compares scheme+host+port to `ABB_WEB_ORIGIN` exactly; `null` Origin is rejected. (d) `Sec-Fetch-Site` reaches the API only if the Next proxy forwards it; browsers cannot forge it but any non-browser client can, so the API should accept it only from the proxy hop (it has no cookie otherwise, so the risk is nil; state it to avoid a future "trusted header"). (e) Log-out must revoke the row *and* clear the cookie with the same attributes, and must succeed (200) even when the cookie is already invalid.
- **C-10 (P2) `login_states` grows without bound (plan:L327 says rows "expire and are deleted on use").** Unused rows are never deleted: `GET /v1/auth/login` is unauthenticated and inserts one row per call, and retention is Phase 19 (and `abb_runtime` can DELETE here, so it is doable now). Correction: on each insert, delete rows with `expires_at < now()` (bounded, e.g. `LIMIT 100` via a subselect), and cap rows per process window through the C-3 limiter. Same for `sessions`: expired/revoked rows should be purged opportunistically on login (bounded), or the table is append-only in practice.
- **C-11 (P3) plan:L104 idle expiry "slid at most once per 5 min"** means the idle window is effectively `idle_hours + 5 min`; fine. But say whether a stream (which re-validates every 30 s) slides the idle timer; if it does, a tab left open keeps a session alive for 7 days, which is the absolute bound anyway. OK either way, just state it.
- **C-12 (P3) DB down during session validation.** `require_principal` maps connectivity errors to `503 DEPENDENCY_UNAVAILABLE` (`auth/dependencies.py:39-45`); keep that for sessions (never `401`, or the web would redirect everyone to login during a blip). Add to AC-5.
- **C-13 (P3) IdP error relay.** `/v1/auth/callback?error=...&error_description=...` must not echo `error_description` into the login page unescaped or into logs verbatim (it is attacker-influenced in some flows). Map to a fixed code.

Verified correct (no finding): opaque random 32-byte session with `sha256` at rest and lookup by hash (no timing oracle, matches the key design); PKCE verifier server-side (confidential client); `state` row deleted on use (code replay with our state fails); bearer wins when both credentials are present; `SESSION_INVALID` uniform.

## D. Next.js <-> FastAPI trust boundary

- **D-1 (P2) plan:L236-238 Node `fetch` follows redirects by default.** The relay for `/api/auth/login` and `/api/auth/callback` will receive a `302` from the API; with the default `redirect: "follow"`, `fetch` follows it to the IdP (login) or to the app page (callback) and the `Set-Cookie` and `Location` are lost. Correction: `redirect: "manual"` in the auth route handlers, relay `Location` and every `Set-Cookie` (use `headers.getSetCookie()`), and a vitest case for each. The plan's risk 3 (plan:L335) does not mention this.
- **D-2 (P2) plan:L219, L237 forward only `abb_session` (and `abb_login` for the auth routes), `X-ABB-Workspace`, `Origin`, `Last-Event-ID`, `Accept`; strip everything else, in particular `Authorization`, `Cookie` (other names), `X-Forwarded-*`, `Forwarded`, `X-Request-ID` (API already sanitises, but do not let the browser set it), `Content-Length` mismatches.** The plan says "only the `abb_session` cookie"; make the header allowlist explicit so that no future "trusted" header can be injected from the browser (ties to C-3).
- **D-3 (P2) plan:L237 new allowlist entries need the same strict id regexes as today's.** `members/{user_id}`, `invitations/{id}`, `api-keys/{key_id}`, `projects`, `audit`, `me`, `pricing/overrides`, `cost/rebuild` with `[A-Za-z0-9_-]{1,64}` segments; reject `..`, `%2F`, `;`. Also decide: is `/api/abb/v1/auth/*` reachable through the generic proxy or only through the dedicated `/api/auth/*` handlers? It must be the latter (the generic proxy would otherwise relay a `Set-Cookie`).
- **D-4 (P3) After the shared key is gone, every server-to-server call is cookie-authenticated or public.** Checked: `app/api/health/route.ts` calls `/readyz` (public, no tenant data); server components call `/v1/me` and `/v1/projects` with the forwarded cookie. There is no remaining path that needs a service credential. OK. Record in ADR-060 that the API must never trust the Next server's network position (no "internal" bypass), so a reachable API port is not a hole.
- **D-5 (P3) CORS.** `main.py:114-120` allows `GET` from `ABB_CORS_ORIGINS` without credentials. Keep `allow_credentials=False`; the cookie is host-only for the web origin and the browser never talks to the API directly (CSP). State in the plan that `ABB_CORS_ORIGINS` must not be widened as part of this phase.

Verified correct (no finding): the proxy's base URL is fixed (`ABB_API_INTERNAL_URL`), so no SSRF via path; CSP `connect-src 'self'` holds; `X-ABB-Workspace` from the browser is only a selector (membership is checked server-side), so spoofing it yields a 404.

## E. Migrations and data model

- **E-1 (P1) plan:L144-148, L231-232 and D11: audit of every user denial is an unbounded, un-deletable write path controlled by any member.** `abb_runtime` loses UPDATE/DELETE/TRUNCATE on `audit_log` (correct for INV-1), retention is Phase 19, and "the UI never hammers a denied route" (plan:L341) is not a bound: a VIEWER with `curl` and their cookie loops `POST /v1/api-keys` and writes one audit row per request, each in its own transaction (plan:L207-208), forever. That is a disk-fill the operator can only fix with the owner credential. Correction (pick one, state it): (a) audit denials through structured logs only, like key denials; or (b) keep rows but coalesce per `(workspace, actor, action)` into at most N rows per minute with a `count` column, enforced in `audit.py` with an in-process bound; or (c) make denial audit subject to a per-actor token bucket (`InMemoryRateLimiter`, `max_keys` bounded) and drop beyond it with a log line. (b) or (c) keep the forensic value. In every case the audit insert must not run inside the request's own transaction (the plan says this, good) and a failure to audit must not turn a `403` into a `500` leak of internals.
- **E-2 (P2) plan:L225 `users` unique `(provider, provider_subject)` nullable pair.** Postgres unique indexes allow many NULL rows (fine for pre-provisioned users), but the email uniqueness is `lower(email)` only, so two IdPs (future) with the same email collide by design. For this phase (one issuer) OK; record that `provider` is the issuer URL, so changing `ABB_OIDC_ISSUER` orphans every linked subject (see C-1 for the re-link path).
- **E-3 (P2) plan:L229-230 `invitations.token_hash unique`, `invited_by -> users.id`, `accepted_by -> users.id`.** Add `CHECK (role IN ROLES)` (the plan says so) and a partial unique index on `(workspace_id, lower(email)) WHERE accepted_at IS NULL AND revoked_at IS NULL`, otherwise "200 open invitations per workspace" can be reached with 200 invitations for one email and the UI has no way to show "already invited". Also store `email` lower-cased at insert (the acceptance compares case-insensitively; a mixed-case stored value is a footgun).

## F. Test strategy

- **F-1 (P1) plan:L251 the completeness test keys on `openapi.build_document()`, which only sees routes with `include_in_schema=True` and whatever `get_openapi` renders.** A route registered with `include_in_schema=False`, a mounted sub-app (the fake OIDC provider is a Starlette app "mounted in-process for pytest", plan:L117: make sure it is mounted only in the test app, never in `create_app`), a `WebSocketRoute`, or a plain Starlette `Route` added via `app.add_route` would not appear and would silently skip the matrix. Correction: enumerate `app.routes` recursively (`APIRoute`, `Route`, `Mount`, `WebSocketRoute`), assert every route is either in `CASES` (keyed by `(method, path)` for every method in `route.methods`, including the implicit `HEAD`) or in a literal `PUBLIC = {("GET","/healthz"), ("GET","/readyz"), ("GET","/docs"), ("GET","/openapi.json"), ("GET","/redoc"), ("GET","/docs/oauth2-redirect")}` set; fail on `Mount`/`WebSocketRoute` unless listed. Keep the OpenAPI assertion as a second check, not the only one.
- **F-2 (P2) plan:L253-257 the matrix test must also run every case with method `HEAD` for GET routes and `OPTIONS` through CORS** (OPTIONS is answered by `CORSMiddleware` before auth only for a real preflight; a non-preflight OPTIONS reaches the router and must be 405, not a data response). Cheap to add, closes the "HEAD returns headers that reveal size" oracle (`Content-Length` of a 404 vs a 200 is identical today because bodies are identical; keep it that way).
- **F-3 (P2) plan:L259-261 the canary string cannot detect numeric or id-only leaks.** Analytics (`/v1/analytics/*`) return counts, costs and `run_id`s of top runs; `/v1/audit` returns `resource_id`s; `GET /v1/members` returns `user_id`s. A cross-tenant bug in a rollup window (`analytics/rollup.py:108-238` filter by `ws`) would add globex's numbers to acme's totals with no canary. Correction: seed globex with distinctive magnitudes (e.g. exactly 7 runs at cost 777.777) and assert acme's totals equal the acme-only expectation; for id-bearing lists, assert no returned id belongs to the globex seed set. Also scan SSE frames for a bounded time (two polls) and scan error bodies, not just 2xx.
- **F-4 (P2) plan:L255-256 "a separate test asserts the literal table equals the code's matrix" is only non-tautological if the literal table is complete.** Make the equality test assert *both* directions and that every `(actor, route)` pair in `EXPECTED` is one of `allow|deny|401|404`, so a missing cell fails rather than defaulting. Also assert the matrix has no `Own(...)` for session-less actors (keys) and no write action for any role, as data invariants.
- **F-5 (P2) plan:L290 `--collect-only | tail -1` is not an acceptance criterion a reviewer can check without knowing the expected number.** Write the expected count into the plan at completion (e.g. `32 routes x 22 actors = 704`), and have the test itself assert `len(CASES) == len(expected routes from F-1)`.
- **F-6 (P3) plan:L266 "stream re-auth after revocation (socket test, test clock)".** `StreamService.frames` uses `loop.time()` (`streaming/service.py:69-73`), not the injected `Clock`; the re-auth interval will need either the loop clock with a small setting or a refactor to the injected clock. Say which so the test is not flaky.
- **F-7 (P3) AC-8 "exactly one audit row" per action.** With E-1's coalescing or dropping, the criterion needs rewording ("at least one row, and for a single action exactly one").
- **F-8 (P3) Mutation checks (plan:L309).** Add: "remove the `cookie == query.state` comparison" (C-2), "allow email linking when `provider_subject` is set" (C-1), "forward `Authorization` in the proxy" (D-2), "drop the last-owner lock" (B-4, needs a concurrency test to catch).
