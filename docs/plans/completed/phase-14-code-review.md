## P1 (must fix before merge)

### P1-1 An agent key can pre-claim the server's derived event ids and silently erase the record of a decision

- Severity: P1 (integrity of the flight record; contradicts ADR-141 point 3 "exactly one event per transition" and threat row "a hostile SDK forging the policy record: closed").
- Where: `apps/api/src/abb_api/approvals/events.py:62-66` (`derived_event_id` is SHA-256 over public inputs only: workspace, approval id, transition name), `apps/api/src/abb_api/approvals/lifecycle.py:36-44` (`emit` raises only on `rejected`; a `conflict` or `duplicate` outcome is swallowed), `apps/api/src/abb_api/ingestion/store.py:160-176` (`ON CONFLICT DO NOTHING` on `(workspace_id, event_id)`; a different body under an existing id is reported as `conflict`, stored nothing), `packages/event-schema/src/abb_event_schema/ids.py:20` (a client event id is any `evt_` ULID whose first character is 0-7; every derived id satisfies that).
- Exploit (VERIFIED, scratch test `test_zz_review_preclaim.py` on the copy; output `GRANTED EVENTS: 0 CONSUMED EVENTS: 0`): the agent asks (`/v1/policy/decide`), receives `apr_...`, computes `derived_event_id(ws, "approval", apr_id, "APPROVED")` and `(..., "consumed")` from the open-source derivation, and ingests two innocuous `tool.call.completed` events with those ids through `/v1/events/batch` (202, both accepted). The human then approves (200) and the agent consumes (200, the approval is spent and the push happens), but the run holds **no** `approval.granted` and **no** `approval.consumed` event: the server's inserts were `conflict`s and nothing noticed. The same works for `approval.denied`, `.expired`, `.cancelled`, the `policy.action.blocked` written by a consume refusal (id derived from approval id and policy version, `service.py:600-603`), and for allow/deny decisions with an `idempotency_key` (`service.py:314-318`: the client picks the key). The attacker's own event, with any non-reserved type and content, sits at that id. The audit log still has the row, but the run page, replay, the summary (`approval.*` events drive `WAITING_FOR_APPROVAL`) and the Phase 13 detectors read events. ADR-141's reserved emitter name and reserved types do not help: the forged event is neither.
- Correction: make server event ids unforgeable and make a conflict loud. (a) Derive ids with a server secret: `HMAC-SHA256(settings.<server secret>, material)` (or a per-workspace secret stored once), so a client cannot compute them; keep the determinism that gives idempotent redelivery. (b) In `lifecycle.emit`, treat `outcome.conflicts > 0` (and ideally `duplicates` with a different body) as an error: log at WARNING with the reason code and fail the transaction (`500`/`409`), since with (a) only a genuine bug or an attacker can produce it. (c) Add a test that pre-claims the `APPROVED` and `consumed` ids before the decision and asserts the server's events still land (the scratch probe above is a ready fail-before test). (d) Amend ADR-141 point 3 and the threat table; the runbook's "every decision is an event on the run, written by the server" depends on this.

## P2 (should fix)

### P2-1 SDK: a malformed `deny` reply falls OPEN

- Where: `packages/sdk-python/src/blackbox/policy.py:229-238` (`_parse_verdict` returns `None` when `policy_version` is missing or not an int, or `policy_id` is not a string, before it looks at `decision`), `policy.py:395-397` (a `None` verdict goes to `_fail`, which is `open` for R0-R2 and unclassified).
- Failure scenario: a server change that renders `policy_version` as a string (or a proxy that rewrites the body) turns every `deny` on an R0-R2 or unclassified action into `Decision(via="fail_open")` plus a warning. Same shape for a 2xx `require_approval` without `approval_id`/`expires_at` (`policy.py:405-406`): a rule that asked for a person falls open. The fuzz and mutation tests cover "a deny returned as allow" but not "a deny the parser throws away".
- Correction: read `decision` first; if it is `"deny"` raise `PolicyDenied` whatever the rest of the body looks like; if it is `"require_approval"` and the approval fields are unusable, fail **closed** (ADR-142 point 4's rule: a human gate is not an availability feature). Add both as mutation-style tests.

### P2-2 Attribute matching silently ignores arguments past the 32nd sorted key and strings over 1,024 characters

- Where: `apps/api/src/abb_api/approvals/intent.py:103-115` (`attributes_of` walks keys in sorted order and stops at 32; long strings are dropped), `apps/api/src/abb_api/policies/evaluator.py:51`. The SDK sends up to 512 values and does not warn (`policy_intent.py`).
- Failure scenario: a rule `when: {capability: github.push, attributes: {force: true}} -> require_approval` above a broad `allow`. An intent whose arguments hold 32 keys that sort before `force` (or an unlucky tool with many arguments) never presents `force` to the matcher, so the push is allowed with no approval, and the hash still covers all arguments so nothing looks wrong. This is a policy bypass inside the cooperative model (a cooperative agent with a wide tool schema hits it by accident; a hostile one on purpose).
- Correction: refuse the intent (`422 INTENT_INVALID`, reason `too_many_attributes` / `attribute_too_long`) instead of truncating, or match on every top-level scalar (the bound exists for cost; 512 values is already the cap). Mirror the rule in `policy_intent.build_intent` so the SDK never sends one. Make the dry-run mapping agree.

### P2-3 `shell.execute` intents carry only the executable name: the approver cannot see the command, and the approval binds to any command of that shape

- Where: `packages/sdk-python/src/blackbox/coding.py:1241-1254` (`guard_command`: resource `executable_of(command)`, arguments `{category}`), `apps/api/src/abb_api/policies/mapping.py:69-78`, ADR-142 point 9.
- Failure scenario: the starter policy's "R3 shell commands need a person". The agent asks for `git` (R3, `category=...`); the approver's panel shows capability `shell.execute`, resource `git`, risk `R3` and nothing else, and approves. The hash is over `{shell.execute, "git", R3, {category}}`, so the approval authorises **whichever** `git` command of that class the recorder runs next in that run and agent (`git push --force origin main` and `git push origin main` are the same intent). D4 says the approver sees the arguments after scrubbing; here there are none to see, and "exactly one action" is "one command of this shape". The whole hash-over-unscrubbed design exists so the server can store a scrubbed command while binding to the real one, and this path does not use it.
- Correction: send the command as an argument (`arguments["command"]`), already masked by the recorder's `sanitize` or left raw for the server scanner (the server scrubs before storage either way), and add `shell.command` to the dry-run mapping's attributes so parity holds (`mapping.py` reads it already). If the choice to exclude the command is kept, say so in the runbook's "Approving" section and in ADR-142 ("the approver of a shell command sees the executable and the risk class only"), and in the panel.

### P2-4 An approval whose content the scanner withheld can still be approved, and the panel blames the approver's role

- Where: `apps/api/src/abb_api/approvals/service.py:385-399` (`arguments = None` when the scan failed or the scrubbed JSON outgrew 60,000 bytes; `scrub_dropped=True`), `apps/web/src/components/ApprovalDetailPanel.tsx:196-197` ("Content hidden by your role." is shown for `content_withheld`, which is the scanner's verdict, not a role).
- Failure scenario: an argument blob that the scanner cannot clear (too large, out of time, scan error) produces a request with no resource and no arguments; the Approve button is live; the approver, who holds `payload.read`, reads that their role hides the content, assumes it is fine and approves an action they could not inspect. A hostile agent can trigger "withheld" at will (a 60 KiB argument).
- Correction: refuse decisions on withheld content (`409 APPROVAL_CONTENT_WITHHELD`) unless the rule opts in, or at least require an explicit acknowledgement in the form and fix the copy ("The arguments could not be scanned and were not stored; you are approving an action you cannot inspect."). Store `scrub_dropped_reason` so the panel can say why.

### P2-5 SDK: a `CANCELLED` approval under `on_expiry: allow` proceeds

- Where: `packages/sdk-python/src/blackbox/policy.py:562-572` (`_settle`: any state other than `APPROVED`/`DENIED` with `on_expiry == "allow"` returns `Decision(via="expiry_allow")`); the wait response's `on_expiry` is read for `CANCELLED` too.
- Failure scenario: a rule says `on_expiry: allow` (the author accepts "nobody answered in time"). The request is cancelled instead (another thread's `aguard` cancellation, an interrupted sibling process that shares the key and withdraws by id, an operator tool): the action proceeds without a person and without an expiry having happened. A cancellation is "the agent withdrew", never "time ran out".
- Correction: only `state == "EXPIRED"` may yield `expiry_allow`; `CANCELLED` is always `ApprovalExpired`/denied. One test.

## P3 (optional / record in KNOWN_ISSUES)

- P3-1 Consume accepts an approval granted under a weaker `approver_role` than the current policy requires (`service.py:529-557`; ADR-141 Amendment 1 proceeds on `require_approval`). Scenario: the rule is tightened from `developer` to `owner` after a developer approved; the old grant still spends. Suggest: when the current decision is `require_approval`, require the deciding user's current role to satisfy the current rule's `approver_role`, or document.
- P3-2 The expiry timer fired early by the database clock is lost (`approvals/job.py:29-31` stamps the application clock; `store.expire_due` finds nothing due and the outbox job completes, never re-enqueued). Safety holds (every read and the consume sweep lazily; the trigger refuses a late spend) but `approval.expired` and the audit row arrive only when someone reads. Suggest: re-enqueue at `expires_at` when the approval is still open.
- P3-3 Waiter slot leak: `self.waiters.enter(...)` precedes `self._hub.subscribe(...)` outside the `try` (`service.py:465-469`); a subscribe failure leaks a slot for the process lifetime. Move `enter` inside the `try` or subscribe first.
- P3-4 `decide` creates the run (and agent) when none exists (`service.py:244-247`, `lifecycle.emit` through `PgEventStore.ingest`), so a `policy:check`-only key can create runs and events in its project, bounded only by the 1,200/min budget. Consider `RUN_NOT_FOUND` for an unknown run from a key without `events:write`.
- P3-5 The open-request caps are checked with count-then-insert under the per-intent lock only (`service.py:361-374`): N concurrent asks with distinct intents overshoot 100/1,000 by up to N. Acceptable; say "approximately" in the runbook.
- P3-6 Budget interplay: `aguard` polls every 5 s (`CANCELLABLE_ROUND`), so 100 pending approvals on one key spend the whole 1,200/min key budget on waits; the 429s count as failed rounds and five in a row cancel the approval (`policy.py:493-501`). Treat 429 with `Retry-After` as "pending", not a failure, or exclude `wait` from the budget.
- P3-7 A server `Date` far ahead of the client shortens the wait budget to the 5 s margin (`policy.py:450-453`), after which the SDK cancels a live approval and raises `ApprovalExpired`. Never an allow, but a clock-skewed server denies every approval. Clamp `server_now` to within, say, 10 minutes of the local clock.
- P3-8 `APPROVAL_INTENT_MISMATCH` and the other consume refusals leave only a log line (`service.py:623-626`), no audit row; ADR-141 point 6 says "counted in the log". A replay attempt is the security event this phase exists to catch: a bounded `approval.consume_refused` row (reason code only) as for the policy-denied case would let the audit page show it.
- P3-9 `BlackBox.guard(..., run=None)` with no current run follows the fail mode with `invalid_intent` (`policy.py:374-375`): R0-R2 and unclassified actions get a silent `fail_open` (no run, so no `policy.warning`). The module-level `guard()` returns `via="disabled"` for the same situation. Pick one and document it in ADR-142; the MCP README already says calls outside a run pass through.
- P3-10 CI uploads `${{ runner.temp }}/policy-e2e-logs` on failure (`ci.yml`), which includes `oidc.log` from the development-only fake provider; if it logs authorization codes or id tokens they are short-lived and local, but the comment "they hold no ... key tokens" is ASSUMED for that log. Verify once or exclude `oidc.log` from the upload.

## Candid assessment

The cooperative wording is where it must be. The single most dangerous residual risk is the combination of **fail-open for R0-R2 and unclassified actions** (every MCP tool call is unclassified and so fails open) with **KI-152** (the `policy.warning` is dropped after the SDK's eight-second retry window): during an outage longer than that, every low-risk and tool action proceeds and the run shows nothing. Added to P1-1, an agent key holder can also erase the server's own record of what the policy decided while the approval still spends. Fix P1-1 before merge; put the fail-open-with-no-trace case in the runbook's first paragraph and give `policy.warning` a durable spool in the SDK's next minor.
